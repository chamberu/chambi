Multiple Replicas ​

Running more than one replica of an agent app relies on the store. Core, the TypeORM store, HTTP intake and @chamvi/channel-cron coordinate through that shared store.

What core already guarantees ​

With a shared, durable store such as the TypeORM store (MemoryStore cannot be shared), several Engines coordinate without a leader:

  • One executor per run. Run claims are leases (claimTtlMs, renewed every third of it). A replica that loses its lease stops writing.
  • One run per concurrency key. Checked under a store lock, across replicas.
  • Shared numerical ceilings. Agent and subscription concurrencyMaxRuns count running runs under an agent admission lock. Waiting approvals release numerical capacity but keep their keys. All replicas must use compatible definitions and complete admission operations inside the lock TTL. CHAMVI_MAX_CONCURRENT_RUNS is still local to each engine, not a fleet cap. See Concurrency.
  • One run per idempotency key. dispatch() claims the key atomically; redeliveries to any replica return the same run.
  • Crash recovery. Every replica's poll requeues runs whose claim expired, and the next execution continues from the latest checkpoint.
  • Graceful drain. A terminating pod marks its unfinished runs interrupted and another replica picks them up.
  • Cross-replica cancel. cancel() on any replica reaches the run's owner on its next poll.
  • One approval message. A store lock per approval plus the message key (<runId>:<approvalId>) the channel dedupes on; a tool's emit() is recorded as an effect, so a redone step sends once.
  • Cron once per tick. The cron channel (@chamvi/channel-cron) takes a store lock per subscription and scheduled time (never released, so a late replica cannot fire the same tick again) and dispatches with an idempotency key built from the same pair. engine.drain() stops it before draining the runs.

Give each replica a distinct owner (the default <hostname>-<pid> already is in Kubernetes). See Concurrency, Leases & Multi-Replica.

Webhooks and deployment ​

The HTTP app can accept deliveries on any replica. GitHub uses the delivery id as its default idempotency key, so a redelivery to another replica deduplicates through the shared store. A 202 means durable acceptance, not execution completion. Excess work remains queued, without a storage bound; use channel HTTP policies separately from execution ceilings.

The Helm chart defaults to one replica with the Recreate strategy. Raising the replica count requires a shared store and compatible definitions. Ingress settings do not configure the app's trustProxy; see Ingress client addresses.
