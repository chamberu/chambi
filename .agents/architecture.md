# Architecture

## Core Concepts

App, Agent, Channel, Run, Step, State, Tool, Workspace, Store. Keep the concept surface at about ten. chamvi never wraps the AI SDK: models (`LanguageModel`), messages (`ModelMessage`) and tool sets (`ToolSet`) are passed through as-is.

`@chamvi/core` holds: agent definitions with channel subscriptions and tool hooks, the `IChannel` contract and the tool-driven outbound (`ToolContext.channels`, `consoleChannel()`), the `Engine`, step checkpoints, budgets, effect tools, durable approvals (`approve()`, answered by run and approval id), recovery and drain, agent state, streaming deltas, structured output, run artifacts (attachments and tool files), the `IStore` interfaces, `MemoryStore`. Everything time-based goes through an injectable `IClock` (`systemClock`; `ControllableClock` in tests). The public surface is `src/index.ts`. `@chamvi/test-kit` exports `describeStoreContract` and `ControllableClock`.

## Engine

`new Engine({ store, agents, ... })` validates at construction (`InvalidAgentDefinitionError`): agent and channel names unique (channel names follow the agent-name rule, `assertChannelName`), every subscription must name a registered channel (`assertRegistrable`: `Agent "<a>" subscribes to unknown channel "<c>".`). Defaults: `claimTtlMs` 60 s, `maxConcurrentRuns` 4, `owner` `${hostname}-${pid}`, `clock` `systemClock`, `onError` logs to `console.error`. `start({ channels? })` recovers, starts every channel (see [Channels](#channels-and-the-envelope)) and begins polling; `dispatch`, `cancel`, `approve`, `tick`, `recover` and `drain` are the operations; `provide(key, value)` (`IContextProvider`) holds the values tools inject (see [Context](#context)). The engine is the one source of what an app is built from: `store` and `clock` are public readonly fields, `getAgent(name)` and `listAgents()` (registration order, a new array) read the registered agents and `getChannel(name)`/`listChannels()` the channels, so channels and `@chamvi/http` take only the engine. `on(type, listener)` is typed per event (`run.updated` carries `run`, `step.appended` carries `step`, `run.delta` carries `delta`) and sees local events only.

**Live registry** (`engine/registry/`, plan 025a): the agent set changes at runtime. `putAgent(agent, { revision? })` registers an agent or replaces the one of the same name in place (a new one goes last), refusing a subscription to an unknown channel like the constructor (`assertRegistrable`), and resolves `added | replaced | unchanged` (`unchanged`, no event, for the same object at the same revision); `removeAgent(name)` resolves whether it was registered here; `agentRevision(name)` is the revision an agent was registered at (`undefined` for a code agent). Both emit `agents.changed` (`AgentChange { name, kind: 'added' | 'replaced' | 'removed' }`, local; `EngineEvent = RunEvent | AgentChange`). Every marker operation runs under the store lock `agents:<name>` (`withAgentLock`, owner a fresh `randomUUID()` per attempt, TTL `AGENT_LOCK_TTL_MS` 300 s, retried every `claimTtlMs / 3` on the `IClock`, `InvalidRunStateError` after 300 s): with a `revision` (a folder's content hash), `syncRevision` reads the marker and, when it differs, cancels the agent's unsettled runs (`queued | running | waiting | interrupted`) created before `changedAt = now` (only when a marker existed: a first sight cancels nothing), then writes `{ agent, hash, changedAt }` (`changedAt` taken right before the write) and sweeps again for runs created before it (a replica at the old hash may create and start one until the write lands), so a change cancels once across replicas; while it syncs, this engine starts no run of the agent (`syncing`, checked by `prepareStart` and `isCurrent`); without one, replacing a registered agent cancels its unsettled runs created before now. `removeAgent` first unregisters the agent and emits `removed` (no further dispatch here), then `dropRevision` cancels all unsettled runs and deletes the marker when one exists (also for an agent this engine never loaded), unless this engine had the agent at another revision (a newer one registered elsewhere: marker and runs left alone); without a marker it cancels the runs of an agent registered here (code or folder: no replica runs it any more, so a lagging replica's runs never stay queued). Cancels run concurrently through `engine.cancel` (a run settled or gone meanwhile is skipped, other failures go to `onError`). `dispatch` for an agent the engine does not hold throws `AgentNotFoundError` (`agent_not_found`, http 404).

## Agents

`defineAgent({...})` takes a typed config object and returns `{ name, definition }` with the budget defaults applied (`maxSteps: 20`, `timeoutMs: 15 min`). Agent names match `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 chars, unique per app; `channels: ChannelSubscription[]` (subscription ids unique per agent, `InvalidAgentDefinitionError` otherwise). `tools` is a plain `ToolSet` or a factory `(ctx: ToolContext) => ToolSet`, called per execution. `assembleTools` builds one `ToolContext { run, state, artifacts, channels }` per execution (shared by the factory and every call) and passes it as the `ToolLoopAgent`'s `toolsContext` (`as never`: a `ToolSet` infers no context type) only to tools whose `contextSchema === toolContextSchema` (`tool/`: `defineTool()`, `defineEffectTool()` and the state tools set it; `validate` returns the value by identity and rejects a non-object, which fails the run, since the AI SDK validates the context outside its tool-error handling). The agent's `toolsContext?: Record<string, unknown>` entries go unchanged (by reference, never cloned or stored) to tools that are not chamvi's (also to one without a `contextSchema`); an entry naming a chamvi tool or no tool is an `InvalidAgentDefinitionError` (`assertToolsContext`, `agent/helpers.ts`: thrown by `defineAgent` for a plain set, a failed run before any model call for a factory), and a third-party tool with a required `contextSchema` and no entry (or a rejected one) fails the run. `toRunError` turns that AI SDK `TypeValidationError` (`context.field === 'tool context'`) into a `ValidationError` naming the tool and the issue paths only, since the SDK's message (and some validators' issue messages) hold the entry's value, which may be a secret; chamvi's own missing-context issue keeps its message. `StepResult.toolsContext` is never stored (steps are built field by field). `artifacts` (`IRunArtifacts`: `put`, `get`, `list`) is scoped to the run (`get` of another run's artifact is `undefined`) and is no effect by itself (wrap `put` in `defineEffectTool` for exactly once). `output` takes an AI SDK `Output` (`Output.object({ schema })`), passed to `ToolLoopAgent` as is. `hooks: { beforeToolExecution?, afterToolExecution? }` run inside `wrapToolsForRun` for every tool of the merged set (user, chamvi, state, third-party; see [Approvals and hooks](#approvals-and-hooks)). An AI SDK tool declaring its own `needsApproval` is refused (`assertNoNeedsApproval`, `agent/helpers.ts`: `defineAgent` for a plain set, a failed run before any model call for a factory), since nothing answers that request. `toolPolicy(toolName, { run })` is applied to the merged tool set (state tools included) in `assembleTools`: the allowed names become the `ToolLoopAgent`'s `activeTools`, so a refused tool is never offered to the model, while every tool stays in `tools` so a pending call that runs after an approval (policy tightened before the resume) still reaches `wrapToolsForRun`, which re-checks every call and answers a refused one with a `ToolNotAllowedError` tool error (the run goes on). A model that calls a refused tool anyway gets the AI SDK's `NoSuchToolError` answer (the tool is not in `activeTools`); `refusedCallError()` (`execute/helpers.ts`) records that tool step as `ToolNotAllowedError` (`tool_not_allowed`), only for a tool of the full set whose invalid call carries a `NoSuchToolError`, so a genuinely unknown tool keeps the SDK's error. The policy should depend only on the run snapshot, so the tool set is stable across executions. `requireToolPermission({ withoutInvoker? })` (`permission/`) offers a tool when the invoker holds `tool:<agent>:<tool>` (`hasPermission`: `*` alone grants everything, a `*` segment matches one segment, segment counts must match; `@chamvi/http` delegates to it); runs without an invoker follow `withoutInvoker` (default `'deny'`).

### Context

`context/` (core): `defineContextKey<T>(name)` returns a frozen `ContextKey<T>`, unique per call (registered in a module-private `WeakSet`; the name is for messages only, an empty or non-string one is `InvalidAgentDefinitionError`). `engine.provide(key, value)` stores the value by reference in the engine's `Map` and refuses a foreign key, also one of another `@chamvi/core` copy a package resolved (`Context "<name>" has no key from defineContextKey() of the engine's @chamvi/core: ...`), `undefined` (`Context "<name>" needs a value.`) and a second value for one key (`Context "<name>" is already provided.`), each `InvalidAgentDefinitionError`; a value provided after `start()` reaches the next execution, since the map is read at call time. There is no `EngineOptions.context`. The engine passes the map as `ExecuteContext.provided`; `assembleTools` binds it to the execution's `ToolContext` through a module-private `WeakMap` (`bindProvided`, `context/helpers.ts`) right after building the context and **before** the tools factory runs, so `inject(ctx, key)` / `tryInject(ctx, key)` return the same object in the factory, in `execute` and in the effect hooks (`alreadyApplied`, `effectKey`). `ToolContext` is exactly `{ run, state, artifacts, channels }` (no own key for a provided value, string or symbol), and nothing provided is stored, cloned or serialized into steps, checkpoints or runs. A spread copy (`{ ...ctx }`) or a hand-built context has no binding: `inject` takes the context the engine passed. `inject` without a value throws `ContextNotProvidedError` (`context_not_provided`, naming the key only, never a value): a tool error in `execute` and in the effect hooks (they run inside the wrapped `execute` of `wrapToolsForRun`), a run failure before any model call in the factory (`assembleTools` rethrows it, `guardedExecute` settles the run `failed` and reports it to `onError`). Feature packages export a core-only pair per shared instance (`provide*Context(engine, value)`, `inject*Context(ctx)`) and keep the key internal. Channels need no pair: `ToolContext.channels` holds run-bound handles (see [Channels](#channels-and-the-envelope)); tools never get the engine itself.

## Channels and the Envelope

A channel (`channel/`, plan 026) is anything a run comes from or talks to; the presence of `start`, `in` and `out` is its only capability:

```ts
interface IChannel<TInput = ChannelRequest, TOutput = Response> {
    readonly name: string;                       // agent-name rules; unique per engine
    readonly defaultAddress?: string;            // emit()/approve() target without an address off the source channel
    start?(ctx: ChannelContext): Promise<void>;  // background intake (cron ticks, sockets, polling)
    stop?(): Promise<void>;
    in?(input: TInput, ctx: ChannelContext): Promise<TOutput>;  // HTTP: { request, subpath }, the raw Request and the raw subpath
    out?(message: ChannelMessage, address: string, opts: ChannelSendOptions): Promise<void>; // idempotent on message.key
}
// ChannelContext { engine, dispatch(envelope) }: dispatch sets `channel` to the channel's own name (createChannelContext)
// ChannelMessage { kind: 'message' | 'approval', key, runId, agent, title?, body, approvalId?, expiresAt? }
// ChannelSendOptions { signal, trigger }: trigger = the run's stored envelope, read only
```

- **Lifecycle**: `EngineOptions.channels: IChannel[]`. `engine.start()` calls every `start(ctx)` after the first `recover()`, sequentially in registration order; a throwing `start` stops the channels already started and rejects `start()`. `engine.start({ channels: false })` starts none (`runJob()`). `stop()` stops the poll and every started channel (`Promise.allSettled`, rejections to `onError`) and returns that promise, so a caller can wait for the channel stops (cron ticks in flight) before closing the store; `drain()` awaits it **first**, then drains. A non-empty `defaultAddress` is checked in the constructor (`assertDefaultAddress`, `InvalidAgentDefinitionError`).
- **Subscriptions** replace trigger definitions: `ChannelSubscription { channel, id, options, concurrencyKey?(p), idempotencyKey?(p) }` on `AgentDefinition.channels`. Each channel package exports a builder named after its default channel whose `on()` makes pure-data subscriptions (`cron.on()` in `@chamvi/channel-cron`, `http.on()`/`webhook.on()` in `@chamvi/http`, `github.on()` in `@chamvi/github`), and the channel factory's instance has `on()` bound to its own name (a second instance). Channels read their subscriptions from `ctx.engine.listAgents()` and follow `agents.changed`.
- **Outbound is tool-driven**: the engine never sends a message of its own, except the approval requests a tool asked for (see [Approvals and hooks](#approvals-and-hooks)). `ctx.channels` (`ToolChannels`, built per execution by `createToolChannels()`, `channel/helpers.ts`, over `engine.getChannel()`/`listChannels()`) hands out run-bound `ChannelHandle { name, address?, emit, approve }`s for channels with `out`: `findOne(name?)` the channel `name` (default the run's `trigger.channel`) or `undefined` when the engine has none of that name or it has no `out`; `findOneOrFail(name?)` the same or `ChannelNotFoundError` (`channel_not_found`, naming the channel only); `find()` every channel with `out` in registration order. A handle on the source channel is bound to `trigger.address`. `emit({ title?, body, key? }, address?)` and `approve({ ..., address? })` default to the source address on the source channel, else to the channel's `defaultAddress` (`consoleChannel()` its name, `openclawChannel()` its `deliver.to`), else need one (`ValidationError` tool error); `emit` and is an effect (`createChannelHandle`, `channel/helpers.ts`): key `<runId>:emit:<channel>:<sha256 of address and canonical message>` (or `key`), recorded through `IEffectStore` like `wrapToolsForRun`, and passed to `out` as `message.key`, so identical emits of one step and a step redone after a crash send once; a throwing `out` records nothing and is a tool error. Outside a tool call (the tools factory) `emit` throws `InvalidRunStateError`.
- `consoleChannel({ name?, write? })` (`channel/console.ts`): out only, default name `console` (also its `defaultAddress`), one header line `[chamvi] <kind>: <title ?? the body's first line> (agent <a>, run <r>, key <k>)`, the body lines, for an approval `approval <approvalId> waits until <ISO>`; never throws.

```ts
type TriggerEnvelope = {
    id: string;              // defaults to a UUID
    agent: string;
    trigger: string;         // the subscription id, e.g. 'http'
    channel: string;         // the channel the run came from, e.g. 'mcp'
    payload: unknown;
    idempotencyKey?: string;
    concurrencyKey?: string;
    address?: string;        // where the run came from on that channel (an issue, a thread, a caller); also Run.address
    attachments?: Artifact[];
    invoker?: Invoker;       // { id, kind, name?, permissions }, from an authenticator only
    receivedAt: Date;        // defaults to now
};
```

Envelopes stored before plan 026 have `source` and `thread`; `normalizeEnvelope()` (`trigger/helpers.ts`, public, used by both store mappers) fills `channel` from `source` and `address` from `thread` when absent and drops both legacy keys (`Run.address` reads the existing `thread` column; no migration).

`dispatch` validates a given invoker (non-empty `id` and `kind`, `permissions` an array of strings, `ValidationError` before any write) and stores a copy of only those fields. It is a snapshot (identity and grants, never a token): a run paused on an approval keeps it, and revoking a grant does not reach a run that holds it. The idempotency scope includes the invoker (see Intake), so a deduplicated dispatch always comes from the invoker of the run it returns. Tool code reads it as `context.run.trigger.invoker` (tools and the factory's `run`) and `ctx.run.trigger.invoker` (effect hooks, agent hooks).

The envelope (channel, trigger, payload) is rendered as a JSON block and becomes the run's first user message: string content, or with attachments `[{ type: 'text', text }, ...one file part per attachment]` whose `data` is the marker `chamvi-artifact:<id>` (`ARTIFACT_URI_PREFIX`, internal). `TriggerEnvelope.attachments?: Artifact[]` holds their metadata; `DispatchEnvelope.attachments?: ArtifactInput[]` takes the bytes.

## Run Lifecycle

Run statuses are exactly `queued | running | waiting | completed | failed | cancelled | interrupted`. Steps are `llm | tool | wait`.

```
dispatch -> queued -> running -> completed | failed | cancelled
running -> waiting (a tool awaits approve()) -> queued (an answer or the timeout) -> running
running -> interrupted (drain) -> queued (recover) -> running
running with an expired claim (crash) -> queued (recover) -> running
```

- **Intake**: `dispatch` first refuses an `idempotencyKey`, `concurrencyKey` or `address` above `TRIGGER_KEY_MAX_LENGTH` (255, the store's varchar width) or with a NUL (`assertTriggerKey()`, `trigger/key.ts`, `ValidationError`, before any store write); channels (`webhookChannel()`, `githubChannel()`) use the same helper. With an `idempotencyKey`, `dispatch` claims `(scope, key)` in the `IIdempotencyStore` (TTL 7 days); the scope is `<agent>:<channel>`, and with an invoker `<agent>:<channel>:<kind>:<id>` with `kind` and `id` each `encodeURIComponent`-ed (`idempotencyScope()`, `trigger/helpers.ts`), so two invokers sending the same key get a run each and one principal cannot squat another's key; a duplicate returns the existing run id with `deduplicated: true`. A key whose run was never created (createRun failed after the claim) is healed by the next dispatch, which creates the run under the reserved id; `createRun` is insert-if-absent, so concurrent healers create it once.
- **Attachments**: `dispatch` validates each `ArtifactInput` (`mediaType` `type/subtype` without parameters, optional string `filename`, `data` a `Uint8Array`; `ValidationError`) before any store write, then, after the idempotency dedupe returned (a duplicate stores nothing), stores each as an artifact of the run (id `<runId>.<index>` from `attachmentIds()` in `artifact/module.ts`, the index zero-padded to one width per dispatch, at least 4 digits, so `listArtifacts` (createdAt, then id) returns the input order; `size` = byte length, `createdAt` = run createdAt) and creates the run. Tool artifacts (`artifacts.put()`) keep `randomUUID()` ids. `storeArtifact` relies on `putArtifact`'s insert-if-absent: when the id is taken by the same run it returns the stored artifact (another run's: `InvalidRunStateError`), so concurrent healers of one reserved key write to the same ids, the second write is a no-op and `trigger.attachments` always names what the store holds (the first writer's bytes). A crash between storing and `createRun` leaves orphan artifacts (accepted; nothing purges artifacts yet), and a racing healer that sends more attachments than the winner leaves its extra indexes listed on the run.
- **Scheduling** (`engine/queue.ts`): a pass lists `queued` runs FIFO (createdAt, then id) and starts them up to `maxConcurrentRuns`. **Execution guard**: a pass that found queued runs first builds a start predicate (`prepareStart`, one `listAgentRevisions()` read, skipped while no folder agent is registered): a run may start when `cancelRequested` (it settles `cancelled`), or when its agent is registered here and is a code agent or loaded at the stored marker's hash; any other run is skipped before any claim and stays `queued` for a replica that has the agent's current revision (never failed with `unknown agent`). `execute()` re-checks after the claim (`isCurrent`, one `getAgentRevision`) and hands a run whose agent was removed or replaced meanwhile back to `queued` (owner-guarded); recovery requeues as before, so the guard also covers recovered runs; `tick()` keeps skipping approval deliveries of unknown agents. A keyed run starts only when no other run of the same agent and `concurrencyKey` is `running`, `waiting` or `interrupted`; check, claim and transition happen under a store lock `concurrency:<agent>:<key>` so it holds across replicas.
- **Claims**: `claimRun(id, owner, claimTtlMs)` is a lease, renewed every `claimTtlMs / 3`. The poll runs on the same interval and calls `tick()` (approval expiry) and `recover()`. Every write of a running run is conditional on status and owner; an engine that loses its lease aborts the execution, writes nothing more and reports a `LeaseLostError` to `onError`.
- **Execution** (`engine/execute.ts`): one `ToolLoopAgent.stream()` call per execution (consumed to the end; settling reads the result's `steps`, `finishReason`, `text`, `output` promises), starting from the latest checkpoint. Checkpoints hold the stored messages (artifact markers); the model gets a hydrated copy whose marked file parts carry the bytes from `readArtifact` (a missing one fails the run with `ArtifactNotFoundError`), and the engine saves `[...storedInitial, ...responseMessages]`, so the pending-call path after an approval works on stored messages. Each `text-delta`/`reasoning-delta` part is emitted as `run.delta` (`RunDelta { runId, step, kind: 'text' | 'reasoning', text }`, `step` = the checkpoint `stepIndex` the step is saved under); deltas are never stored, local to the executing replica and never emitted once the execution was abandoned. No opt-out: every AI SDK provider streams. A model call that fails mid-stream (an `error` part) still ends its step: the AI SDK finishes it with finish reason `error`, so the engine appends the `llm` step (the partial text) and saves its checkpoint before the run fails with that error (unlike the former `generate()`, which wrote nothing; pinned in `stream.spec.ts`). A step whose provider stream closed without its finish part (the AI SDK then synthesizes finish reason `other` and never executes the step's tool calls) fails the run with `IncompleteResponseError` (`incomplete_response`); the engine tells it apart through `onLanguageModelCallEnd`, which fires only for a received finish, so a provider that reports `other` itself still completes.
- **Structured output**: with `output`, a `completed` run's `output` is the parsed value (else the text); a final answer that fails to parse or validate (`NoOutputGeneratedError` or a schema failure) fails the run with `ValidationError` (`validation_error`, message from the cause, the cause cut to `MAX_ERROR_CAUSE_LENGTH` 500 characters plus an ellipsis, `execute/constants.ts`). Before parsing, a loop end with no answer fails with `IncompleteResponseError` (`incomplete_response`, `incompleteOutput()` in `execute/helpers.ts`): finish reason `length` (cut answer) or `tool-calls` outside a budget stop (a call nothing executed, e.g. a tool without `execute`, named in the message). A plain agent keeps completing with the text in both cases (decided: its text is still usable and the llm step records the finish reason). The "step limit reached by an earlier execution" branch parses the checkpoint's last assistant text through `output.parseCompleteOutput` with the same rules (a `length` checkpoint is incomplete). The `ToolLoopAgent` gets `withoutPartialOutput(output)` (`execute/helpers.ts`): a prototype copy whose `parsePartialOutput` returns `{ partial: text }` without parsing, so the AI SDK neither re-parses the accumulated answer per delta nor holds deltas back (returning `undefined` would publish the whole text at `text-end` only); `parseCompleteOutput` and `responseFormat` stay the agent's. After every step the engine appends the steps and saves a checkpoint (messages plus the step's `finishReason`). A cancel or drain abort lets the step-end writes in flight finish (all tool rows and the checkpoint of a completed step), so a recovery does not redo a step whose tools already ran; an abandon guard then stops a still-running generate from writing after the run settled. Each execution owns an `AbortController` combined into the signal the agent and the tools get (`run.signal`); it aborts on every exit, so a throw while consuming the stream (e.g. a throwing `onError` behind a failing `run.delta` listener) cancels the model stream instead of leaving it open.
- **Budgets** (`engine/budget.ts`): `maxSteps` and `maxTokens` are stop conditions, `timeoutMs` an abort signal per execution (built on the `IClock`). Stopped by a budget while the last step asked for tool calls: `failed` with `BudgetExceeded`; otherwise `completed` (a plain agent), or for an agent with `output` the structured-output rules apply (a `length` finish fails with `incomplete_response`). Timeout: `failed` with `Timeout`.
- **Tool errors** go back to the model as tool-error results; only `FatalToolError` (and infrastructure or store failures) fail the run.
- **Cancel**: aborts a local execution (`cancelled`), or marks a `queued`/`waiting` run cancelled. A run `running` on another replica (or `interrupted`) gets `cancelRequested: true`; the owner sees it in `recover()` on its next poll and aborts with stop `cancel`, and an execution that starts on such a run settles it `cancelled` without a model call. A cancel that races a pause (the abort cannot interrupt the `waiting` write) cancels the run the pause left waiting, without delivering the approval.
- **Drain**: `drain({ timeoutMs })` stops every channel first, then stops polling and starting runs, waits for in-flight runs (default 30 s), then aborts the rest and marks them `interrupted` with the claim released. `stop()` stops the channels, then only polling.
- **Recovery**: `recover()` (on `start()` and every poll) claims each `running` or `interrupted` run whose claim expired or was released and requeues it; the next execution continues from the latest checkpoint. A step whose checkpoint never landed runs again.

## Approvals and Hooks

Durable `approve()` (plan 026) replaced the `approvals` map, the AI SDK `toolApproval` path and `approvalTimeoutMs`:

- **Tool-call frame** (`effect/frame.ts`, internal): `wrapToolsForRun(tools, ctx, store, { allow?, hooks?, onSuspend?, stepIndex? })` runs every call inside an `AsyncLocalStorage` frame `{ runId, toolCallId, toolName, stepIndex, approvals, ... }` (`stepIndex` read per call: the checkpoint index of the model step that made the call; the pending calls' checkpoint index while they replay) (`runToolCall`, `currentToolCall`). Order per call: frame, `allow` (`ToolNotAllowedError`), `beforeToolExecution` (its result is the input; a changed one is re-validated through the tool's `inputSchema`, a failure a `ValidationError` tool error), effect lookup and execute (the effect key from the final input), `afterToolExecution` (on a fresh and on a recorded result; a streaming tool's final value; never for a tool error). A thrown `ToolDeniedError` (`tool_denied`) is a tool error, `FatalToolError` still fails the run. Tools without `execute` pass through untouched.
- **`approve(ctx, { title, body?, timeoutMs? })`** (`approval/request.ts`; `ChannelHandle.approve()` is the same with `channel` and `address`): outside a frame, or in a streaming tool's body, `InvalidRunStateError`; `timeoutMs` default `DEFAULT_APPROVAL_TIMEOUT_MS` 24 h, 1 to `APPROVAL_TIMEOUT_MAX_MS` (2^31 - 1), else `ValidationError`. The n-th call of a frame (0-based, taken before any await) has `approvalId = <stepIndex>:<toolCallId>:<n>` (the step index, so a provider that reuses a call id in a later step asks again instead of reading an earlier step's decision); a decision recorded under the effect key `approval:<runId>:<approvalId>` (`approvalDecisionKey`) is returned, else the request is stashed on the frame (the first suspension of the call wins) and an internal `SuspendSignal` thrown. It sends nothing.
- **Suspend**: the wrapper catches the signal, records the request in call order and answers the AI SDK with `SUSPENDED_RESULT` (never stored); a stop condition ends the loop after that step. The checkpoint keeps the assistant message's tool calls and drops the suspended calls' results (`withoutResults`), no `tool` step for them; then `pause()` moves `running -> waiting` with `WaitPoint { kind: 'approval', approvalId, toolName, toolCallId, title, body?, channel?, address?, expiresAt, notifiedAt? }` from the first suspended request in call order (one approval per pause; the others stay pending and suspend again after the resume; parallel identical effect calls share one application, so a call whose shared application suspended stays pending on the same approval and gets the recorded result on replay), releasing claim and slot (a keyed run keeps its key blocked). Re-pausing on the same approval keeps the wait point, so the approval the owner was asked stays answerable; the `approvalId` is the wait point's identity (`answer()` and the delivery compare it).
- **Delivery** (`deliverApproval`): once the wait point is stored and it names a channel, the engine sends, detached from the execution (tracked in `deliveries`, awaited by `idle()` and `drain()`, so a slow `out` holds neither the slot nor the executions entry and a resume meanwhile starts the next execution cleanly; an execution only removes its own executions entry, and the queue never starts a run whose previous execution still holds its slot), `ChannelMessage { kind: 'approval', key: '<runId>:<approvalId>', title, body, approvalId, expiresAt }` (never the token) through that channel's `out` to `waiting.address`, with `{ signal, trigger }`, under the store lock `notify:<runId>:<approvalId>` held for one attempt (aborted after `claimTtlMs`), and records `waiting.notifiedAt`. `tick()` re-sends on every poll while it is missing; a crash before the wait-point write sends nothing, after it re-sends under the same key; a channel the engine no longer has goes to `onError` per attempt. `approve()` without a channel sends nothing (inbox and API only).
- **Answer** (`answer()`): `approve(runId, { approvalId, approved, reason?, approver? })` (`ApprovalAnswer`) and the `tick()` timeout (`approval timed out`, denied) move `waiting -> queued` (guarded by `expectStatus`, so only one answer writes), record the decision with `putEffect('approval:<runId>:<approvalId>', { approved, reason?, approver? })`, append a `wait` step (`name` the tool, input `{ toolCallId, title, body? }`, output `{ approvalId, approved, reason, approver? }`), then clear `waiting`. A failure undoes back to `waiting`, so the wait point stays answerable. `approve()` validates the approver before any store read and refuses a run that is not waiting, another `approvalId` or a wait point at or past `expiresAt` with `InvalidRunStateError`; a run that moved on meanwhile is `InvalidRunStateError` (the `stale` factory, also for the `tick()` timeout, which ignores it).
- **Pending calls** (`engine/execute/`): the next execution first finds the checkpoint's assistant tool calls without a result (`pendingToolCalls`) and runs them in order through the wrapped tool set with their recorded ids (`executePendingCall`), re-applying what the AI SDK would: `toolPolicy` (`ToolNotAllowedError`), the input schema parse (`ValidationError` result), the `contextSchema` check for third-party tools (fails the run), the hooks. After each finished call the checkpoint gets its result first (`withToolResults`, saved under the same `stepIndex`), then its `tool` step, so a drain, crash or lost lease after it never runs it again; no further call starts once the execution was aborted, and an abort waits for that write before settling. A call that suspends again pauses without a model call. Then the model loop starts. The model sees only the tool's result; the decision lives on the `wait` step. Code before `approve()` runs again on resume (documented replay rule, as for crash recovery). A checkpoint with pending calls gets one step beyond `maxSteps`.
- No resume tokens: an approval is answered only by run and approval id (`engine.approve()`, `@chamvi/http`'s authenticated `POST /runs/:id/approve` and MCP `approve_run`), so there is no `resumeSecret` and no message carries a credential.

## Store Contract

The store is a set of small interfaces combined as `IStore` (`src/store/types.ts`):

| Interface | Holds |
|-----------|-------|
| `IRunStore` | Runs; `updateRun` with `expectStatus`/`expectOwner` guards; `listRuns` ordered by createdAt then id (both ascending, or both descending with `order: 'desc'`), unbounded without `limit`; `claimRun`/`renewClaim` leases |
| `IStepStore` | Append-only steps per run |
| `ICheckpointStore` | Latest checkpoint per run (highest `stepIndex`; equal index replaces) |
| `IIdempotencyStore` | `claimKey(scope, key, runId, ttl)`: first caller wins |
| `ILockStore` | `acquire`/`release` of keyed leases |
| `IEffectStore` | Recorded effect results by effect key |
| `IStateStore` | Per-agent KV (`kvSet(..., undefined)` removes the key; `kvList(agent, { limit?, offset? })` in key code-point order, unbounded without `limit`) and document collections (`where` = top-level equality) |
| `IAgentRevisionStore` | One revision marker per folder agent, `AgentRevision { agent, hash, changedAt }` (no code): `getAgentRevision`, `setAgentRevision` (upsert), `deleteAgentRevision` (missing is a no-op), `listAgentRevisions` (agent code-point order); copied in and out |
| `IArtifactStore` | `putArtifact(artifact, data)` (atomic insert-if-absent, `false` keeps the stored one), `getArtifact` (metadata), `readArtifact` (bytes, a plain `Uint8Array`), `listArtifacts(runId)` (createdAt, then id); bytes copied in and out |

Rules every implementation must keep: a TTL created at T with `ttlMs` is expired at exactly `T + ttlMs`; values are copied in and out (no aliasing); atomic operations are atomic across callers. `MemoryStore` implements it in-process (structured clones, no await between check and write). `describeStoreContract((clock) => store)` from `@chamvi/test-kit` is the shared Vitest suite every store must pass; the factory must use the given `ControllableClock` for expiry. Redis is never required.

`TypeormStore` (`@chamvi/store-typeorm`) is the TypeORM store (PostgreSQL only). Every method goes through the entities' repositories and query builders; the only hand-written SQL is the `jsonb_exists` key check in `docList` (TypeORM has no key-existence operator), containment uses `JsonContains`; `store/helpers.ts` maps entities to `Run`, `Step` and `Checkpoint` (a `RETURNING` row is hydrated through the entity metadata). Every atomic operation is one statement: `insert().orIgnore()` returning `id` (`createRun`, `putArtifact`), `insert().orUpdate()` with the overwrite condition `expires_at <= now` returning a row (`claimKey`, `acquire`), a conditional `update()` (`claimRun`, `renewClaim`, the `updateRun` guards, the latter returning `*`) and `insert().orUpdate()` with the overwrite condition `step_index <=` (`saveCheckpoint`). Time comes from the `IClock` as a parameter, never the database's `now()`. Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt` and `waiting.notifiedAt` are revived as `Date`. Only the latest checkpoint is kept. Artifacts live in `chamvi_artifacts` (`ArtifactEntity`: `id` varchar(128) PK, `run_id` indexed, `agent`, `media_type`, `filename` nullable, `size` int, `data` `bytea` with `select: false`, `created_at` timestamptz; migration `1792368000000-artifacts.ts`); `chamvi_idempotency_keys.scope` is varchar(1024) (migration `1792454400000-idempotency-scope.ts`, a hand-written `ALTER COLUMN ... TYPE`, since TypeORM's generated length change drops and re-adds the column); `chamvi_kv.key` is `COLLATE "C"` (migration `1792540800000-kv-key-collation.ts`, `KvKeyCollation1792540800000`, hand-written the same way), so `kvList` orders by code point; markers live in `chamvi_agent_revisions` (`AgentRevisionEntity`: `agent` varchar(64) `COLLATE "C"` PK, `hash` varchar(128), `changed_at` timestamptz; migration `1792627200000-agent-revisions.ts`, `AgentRevisions1792627200000`), `setAgentRevision` a repository `upsert` on `agent` (no compare needed: the engine holds `agents:<name>`), `listAgentRevisions` ordered by `agent`; `getArtifact`/`listArtifacts` never load `data`, `readArtifact` returns a plain `Uint8Array`. `migrateStore(dataSource)` runs the migrations under the advisory lock `chamvi:migrations`; `purgeExpired(now?)` deletes expired idempotency keys and locks (nothing calls it automatically yet). Documented divergences from `MemoryStore`: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, `putEffect(key, undefined)` reads `{ result: null }`, `docUpsert(..., undefined)` reads `doc: null`, `docList` `where` is `jsonb` containment and orders by `id`, `listRuns` ties use `COLLATE "C"`.

## Idempotency and Side Effects

1. Trigger dedupe at intake via `IIdempotencyStore`.
2. Completed steps are never repeated: execution resumes from the latest checkpoint.
3. Side-effecting tools use `defineEffectTool()`. Per call the wrapper (`wrapToolsForRun`) returns the recorded result for the effect key, else asks `alreadyApplied(effectKey, input, ctx)`, else executes and records the result; both hooks get the `ToolContext` (`ctx.run`, `ctx.state`, `ctx.artifacts`), and a custom `effectKey(input, ctx, options)` also gets the AI SDK call options (`toolCallId`, `messages`, e.g. to key by model step). The default key is `${ctx.run.runId}:${toolName}:${sha256(canonical JSON of input)}`. A throwing execute records nothing; a crash between the effect and the record repeats it unless `alreadyApplied` finds it (`effectMarker(key)` is the hidden marker to embed). Parallel identical calls in one step share one application.

## Agent State

`createAgentState(agent, schema, store)`: KV (`state.get/set`) plus typed collections declared as `state: Record<name, StandardSchemaV1>` in `defineAgent`. `upsert` validates with the collection's Standard Schema, mapped through `@validup/standard-schema` (`ValidationError` with the validup `issues` on failure, nothing stored). With a schema, the model also gets `state_<coll>_list`, `state_<coll>_upsert` and `state_<coll>_remove` tools (`createStateTools(schema)`; chamvi tools reading `context.state`, upsert and remove are effect tools); user tools win on a name clash.

## Cron Channel

`@chamvi/channel-cron` (the former `@chamvi/scheduler`) is the cron channel; it depends on `hubwire` (croner inside) and `cron-parser` and is a peer of core.

- `cron.on(expression, { timezone?, overlap?, payload?, id? })` (`subscription/`) makes a subscription of the channel named `cron` (id default `cron:<expression>`); it validates the expression with cron-parser, the timezone with `Intl`, the overlap policy (default `skip`; `queue-one`, `allow`) and a non-empty `id` (`InvalidAgentDefinitionError`). `cronChannel({ name?, owner?, lockTtlMs?, onError? })` (`channel/`) is the channel; its `on()` makes subscriptions only it fires (a second instance, e.g. `cron-eu`), and `cron.on()` ones reach only the channel named `cron`.
- `start(ctx)` runs the internal `createScheduler({ engine, channel, owner?, lockTtlMs?, onError? })`, which builds one hubwire `defineScheduledComponent` per cron subscription of this channel in `engine.listAgents()`, named `cron:<agent>:<subscriptionId>`, with `lock: createStoreScheduleLock(engine.store, owner)` (`ILockStore.acquire`, never released) and `lockTtlMs` default `SCHEDULE_LOCK_TTL_MS` (10 min). hubwire's tick key is `${name}:${scheduledAt ISO}`. A code agent's subscription hubwire refuses (expression croner rejects, timezone) throws `InvalidAgentDefinitionError` out of `engine.start()`; a folder agent's (registered at a revision) goes to `onError` and leaves it unscheduled. `assertSchedulable(agent, channel?)` is the same check without scheduling (the app's `AGENT_CHECKS`).
- Live components: the channel keeps its components per agent (`buildAgentComponents()`, `scheduler/helpers.ts`) and follows `agents.changed`: `added` builds and starts the agent's components, `replaced` stops the old ones and builds the new, `removed` stops them. A replacement hubwire refuses goes to `onError` and leaves the agent unscheduled (never a throw). Retired components stop in the background; `stop()` (called first by `engine.drain()`/`stop()`) unsubscribes, stops every component and awaits their `settled()` plus the retired ones.
- `runOnStart: false` always: a start pass never takes hubwire's lock and would fire on every replica. hubwire skips a locked tick fired `lockTtlMs` or more late; `onSkip` is not wired (N - 1 replicas skip every tick). Lock, overlap and dispatch failures reach `onError(error, { agent, subscription })`.
- `fireCronSubscription({ engine, agent, subscription, scheduledAt })` is one tick: overlap check (over `engine.store`), then `dispatch` with `channel` the subscription's channel, payload `options.payload ?? { scheduledAt: ISO }`, idempotency key `<subscriptionId>@<scheduledAt ISO>` (the subscription's own `idempotencyKey()` is ignored), `concurrencyKey = subscription.concurrencyKey?.(payload) ?? (overlap === 'allow' ? undefined : subscription.id)`.
- Overlap: active runs are `queued | running | waiting | interrupted` of the agent filtered by `run.trigger.trigger`. `skip` skips while any is active, `queue-one` while one is `queued`, `allow` never. The check-then-dispatch race is made harmless by the default concurrency key (the extra run waits).
- `runJob({ engine, agent, subscription?, pollMs?, drainTimeoutMs?, signal? })` fires once at `engine.clock.now()` (the engine must hold the subscription's cron channel), then always starts the engine with `start({ channels: false })` (a job never starts cron schedules or sockets) and calls `engine.tick()` once (so a skipped tick still recovers leftovers of earlier jobs and times out expired approvals), waits via `run.updated` plus an `engine.getRun` poll (`pollMs`, default 1 s, covers another replica) for `completed | failed | cancelled | waiting`, or for `queued` behind a `waiting` run of the same concurrency key (`queue-one` behind an approval), then `drain({ timeoutMs })` (default 30 s). Exit code 1 for `failed`/`cancelled`, else 0; an overlap skip returns `skipped` after the drain. It starts a full engine over the shared store (every queued run of every agent), so size the drain timeout. `signal` (for the CLI's SIGTERM): already aborted when called, it fires nothing and starts nothing (`skipped`); aborted during the dispatch, the engine never starts and the stored run answers (`queued`, exit 0); checked again after `engine.start()`, so a stop that arrived meanwhile skips the approval tick; aborted while waiting, the wait ends and the drain runs, answering the run as the drain left it (`interrupted`, exit 0).

## HTTP

`@chamvi/http` is one routup v6 `App` per chamvi app, a peer of core like the channel packages.

- `createHttpApp({ engine, agents?, auth, basePath?, trustProxy?, shutdown?, bodyLimit?, stream?, mcp?, cors?, rateLimit?, metrics?, readyTimeoutMs?, onError?, routes?, channels? })`. The store (`listRuns`, `listSteps`, state), the agents (all, or the names in `agents`, resolved by `selectAgents()` in `app/helpers.ts` at construction: a name the engine lacks or given twice is `InvalidAgentDefinitionError`; the others, also agents registered later, have no routes or MCP tools in this app, while a mounted channel serves every agent subscribing to it) and the clock come from the engine (`engine.store`, `engine.listAgents()`, `engine.clock`); `buildContext()` copies the store and clock into the internal `HttpContext` and reads the agents live (see Live agents). `basePath` loses its trailing slashes (`normalizeBasePath()`, `app/helpers.ts`; `/` is no prefix), so every reader sees one prefix. An empty `auth` array, a `basePath` that is then no static path (the extra routes' shape) and a `stream.maxOpen` that is no positive integer throw `InvalidAgentDefinitionError`. Order: plugins, health, agents (incl. `/schedules`), runs, channels, extra routes, MCP, a trailing catch-all 404, the error handler. Route modules share one internal `HttpContext` (`app/types.ts`). **Live agents**: `HttpContext.agents` is `HttpAgents { get, list, names }` (`createLiveAgents()`, `app/helpers.ts`), reading `engine.getAgent`/`listAgents()` on every call (filtered by `agents`), so routes, `GET /agents`, `/schedules`, `GET /runs` agent filters, extra routes (`HttpRouteContext.agents` is a getter) and MCP follow `putAgent`/`removeAgent` at once; a named agent removed from the engine answers 404. `agentIssues?: () => readonly AgentIssue[]` (the app's load issues) is read per `GET /agents`, filtered by `agents`.
- **Channels** (`channels/`, `subscriptions/`, plan 026): `httpChannel()` (name `http`) and `mcpChannel()` (name `mcp`) have no `in` and no `out`; they are registered so `http.on({ schema? })` subscriptions (id `http`, at most one per agent) validate and `ctx.dispatch` scopes REST runs as `http` and MCP `run_<agent>` runs as `mcp` (separate idempotency scopes). `webhookChannel({ auth, name?, bodyLimit? })` has an `in` serving `webhook.on(path, { schema?, idempotencyKey?, concurrencyKey? })` (id `webhook:<path>`, many per agent, `path` starts with `/`) at `/channels/<name>/<agent><path>` (`parseWebhookSubpath`): a principal of its own `auth` (required, the app never authenticates channel routes) holding `agent:<agent>:run` checked before the body is read, JSON only (415), `readRequestBody` with `bodyLimit` (default 1 MiB, 413), the whole body is the payload through the schema, `Idempotency-Key` header else `idempotencyKey(payload)`, `202 { runId, deduplicated }`, no invoker on the run. `createHttpApp({ channels })` mounts `POST /channels/<name>` and `/channels/<name>{/*rest}` (`registerChannelRoutes`) for exactly the listed channels, each validated at construction (`validateChannels`: it has an `in` and is the object the engine holds under its name, else `InvalidAgentDefinitionError`); `channels` is a `RESERVED_ROUTE_SEGMENTS` entry, so any other `/channels/...` path is 404 and no `in` runs. The mount is rate-limited but never authenticated; `in` gets `{ request: event.request, subpath }` (raw, percent-encoded, `''` for the bare path) and a `ChannelContext`, its `Response` is returned as is and a thrown error renders through the JSON error handler (a 413 also sets `connection: close`). `readRequestBody(request, { limit })` (public, `request/helpers.ts`, exported next to the channels) is a channel's bounded body read: content-length check, then a bounded read; above `limit` a `RequestEntityTooLargeError` (413). Media-type checks stay with each channel. `GET /agents` summarizes subscriptions as `AgentSummary.channels: [{ channel, id, hook? }]` (`hook` the URL of a webhook subscription of a channel this app mounts, `webhookUrl()`); `routeLabel` labels the mount `/channels/:name/*`.
- Routes: `POST /agents/:name/runs` (the agent's `http.on()` subscription, channel `http`, 404 without one; body `attachments?: Array<{ mediaType, filename?, data }>`, at most `MAX_ATTACHMENTS` 16 (`runs/constants.ts`), validated by `isArrayOf(<attachment Container>, { max: MAX_ATTACHMENTS })` (length checked before any item, item issues prefixed with their index) with `isMediaType` (core's `isArtifactMediaType`, one rule for both packages), `isString` (1 to 255) and `isBase64` (strict RFC 4648 base64, canonical, decoded to a plain `Uint8Array`, never echoing the input in the issue; the other validators pass `boundReceived(value)`, the value only when its JSON has at most `RECEIVED_MAX_LENGTH` 256 characters) from `request/validators.ts`, unknown item keys dropped, passed to `dispatch`; size bounded by `bodyLimit`), `GET /runs/:id/artifacts` (`{ data: Artifact[] }`), `GET /runs/:id/artifacts/:artifactId` (the bytes; `content-type` the stored media type, `content-length`, `content-disposition: attachment` plus `filename`/RFC 5987 `filename*` when named, `x-content-type-options: nosniff`, `cache-control: private, no-store`; both under the run read rule via `loadReadableRun`, an artifact of another run 404 `artifact_not_found`), `GET /runs` (rapiq URL query via `@rapiq/codec-url` 2.4: `filter[agent]`, `filter[status]`, `page[limit]` default 50 max 100, `page[offset]`, `sort=createdAt` (oldest first, the default) or `sort=-createdAt` (newest first, `RunListQuery.order` `desc`, passed to `listRuns`); only `and`-joined leaf filters; page values must be plain integers, as rapiq reads them with `parseInt`; rapiq coerces `123`, `007`, `true`, `null` even when quoted, so a non-string `filter[agent]` maps back to the registered agent whose name coerces to it, 400 when two do), `GET /runs/:id` (run plus steps), `GET /runs/:id/stream` (SSE), `POST /runs/:id/cancel`, `POST /runs/:id/approve` (body `ApproveBody { approvalId, approved, reason? }`, `approvalId` 1 to `APPROVAL_ID_MAX_LENGTH` 255, `reason` at most `APPROVAL_REASON_MAX_LENGTH`; `engine.approve()` with the principal as `approver`, `202 { runId, status: 'queued' }`, `InvalidRunStateError` 409 for a stale `approvalId`, an expired wait point or a run not waiting), `POST /channels/<name>[/...]` (the mount, see Channels), `GET /me` (`me/module.ts`: any authenticated principal, `MeView { id, kind, name?, permissions }` from `toInvoker(principal)`, the one place a principal sees permissions, its own; never the claims), `GET /agents` (`{ data: AgentSummary[], issues: AgentIssue[] }`, `AgentIssue { agent, message, at }`: agents that failed to load), `GET /schedules` (cron definitions with `nextAt`, not scheduler health), `GET /agents/:name/state/kv` (`state:read`, `kvList` in key code-point order as `{ data: Array<{ key, value }> }`, `parseKvListQuery`: `page[limit]` default 50 max 100, `page[offset]`, no filter or sort), `GET/PATCH /agents/:name/state/kv/:key`, `GET /agents/:name/state/collections/:collection` (top-level `eq` filters as `docList` `where`, a double-quoted value kept as a string because rapiq coerces `42`/`007`/`true`/`null`, `filter[id]` 400 since `id` is the store id, `page[limit]`, a `page[offset]` above 0 is 400; documents as `{ id, ...fields }`, a non-object as `{ id, doc }`), `/mcp`, `GET /healthz`, `GET /readyz` (503 `shutting-down`, `draining` or `store-unreachable` within `readyTimeoutMs`), `GET /metrics`.
- Errors: every route under `basePath` answers `{ status, code, message, issues? }`, built by the error handler (never `toJSON()`, which would send `cause`); `withIssues` runs every issue tree through `boundIssues()` (`request/helpers.ts`), dropping a `received` value over `RECEIVED_MAX_LENGTH` whatever produced it (validators, a subscription schema, a core `ValidationError`), so a 400 never echoes a large body. `@ebec/http` errors keep their status (code lower-cased), validup errors are 400 `validation_error`, core codes map `RUN_NOT_FOUND` and `ARTIFACT_NOT_FOUND` 404, `INVALID_RUN_STATE` 409, `VALIDATION` 400 (`INVALID_AGENT_DEFINITION` at request time comes from an authenticator or `oidc()` mapper that resolved an invalid principal: 500 and `onError`); anything else is 500 `Internal Server Error` and goes to `onError`. Every 401 gets `WWW-Authenticate: Bearer`. Error responses start from `event.response.headers`, so CORS, `RateLimit-*` and `Retry-After` survive.
- Auth: `Authenticator = (request) => Promise<Principal | undefined>` (`undefined` lets the chain continue, a throw is a 401 remembered while later authenticators run; a resolved principal without a non-empty `id` and `kind` and a `permissions` array of strings is `InvalidAgentDefinitionError`, 500 and `onError`, and ends the chain); the chain runs once per request (memoized on `event.store`). Built-ins: `staticTokens({ tokens: [{ value, id, permissions }] })` (sha256-indexed, `value` at least 16 characters and unique, a non-empty `id` that several tokens may share), `authup()` (`@authup/server-adapter-web` `verifyRequest`; grants only from tokens whose `scope` has `global`), `oidc()` (vouchly; `principal` mapper and a non-empty `audience` per issuer required, as vouchly skips `aud` without one; untrusted issuer or malformed token passes on, unreachable issuer 503, an unknown `kid` 401; a mapper result without a non-empty `id` and `kind` or with `permissions` that are no string array throws `InvalidAgentDefinitionError`, a 500 reported to `onError`). Permissions `agent:<name>:run`, `agent:<name>:approve`, `run:read`, `run:cancel`, `state:read`, `state:write`, `tool:<agent>:<tool>` (read by core's `requireToolPermission()`, never checked by a route), `*`; a `*` segment matches one segment, segment counts must match. Routes match with core's `hasPermission(principal.permissions, wanted)`; http exports only `agentPermission()`, no matcher of its own.
- Reading runs: `run:read` or `agent:<run.agent>:run` (`GET /runs/:id`, the stream, MCP `get_run`); `GET /runs` and `list_runs` without `run:read` must filter to one agent the principal can run (one store query keeps `total` exact). 404 comes before 403 (run ids are random UUIDs).
- Body after authorization: every protected `POST`/`PATCH` authorizes before `readJsonBody` (so an unauthenticated client cannot make the server buffer `bodyLimit`). `POST /runs/:id/approve` authenticates, loads the run (`loadApprovableRun`, 404, no read permission needed), requires `agent:<agent>:approve` (403), then reads the body. Bodies: JSON media types only (415 at the first non-empty chunk), `bodyLimit` (413; a `content-length` above it is refused unread, which Node discards; a body refused part-way is drained up to `bodyLimit` more bytes, else answered with `connection: close`, because an unread remainder stalls the next request on a keep-alive socket), objects only for REST bodies (validup `Container` with chamvi's own `isString`/`isBoolean`/`isDefined` validators; unknown keys dropped), subscription payloads through the subscription's Standard Schema (`validatePayload`). U+0000 is refused as 400 at the edge (`assertNoNul` on path and query before any route, `isString`, webhook-derived keys and addresses, MCP `pattern`s), since Postgres varchar columns refuse it and a lookup would otherwise be a 500.
- Invoker: `toInvoker(principal)` (`auth/helpers.ts`) snapshots `id`, `kind`, `permissions` and a `name` from the claims (`name`, then `preferred_username`; never `email`, which every reader of the run would see; static tokens have none), never the claims themselves. `POST /agents/:name/runs` and MCP `run_<agent>` dispatch with it as `invoker`; `POST /runs/:id/approve` and MCP `approve_run` pass it as `approver`. Webhook and GitHub deliveries dispatch without one; it never comes from a body.
- `serializeRun()` drops `claim` and the invoker's `permissions` (keeping `id`, `kind`, `name`) from every run that leaves the package (REST, SSE, MCP), `serializeStep()` drops the `permissions` of a `wait` step's `output.approver` (`GET /runs/:id`, SSE): a `run:read` holder must not learn another principal's grants. Wire types `RunView` and `InvokerView` (`runs/types.ts`).
- SSE: subscribe to `engine.on` before the snapshot, send `run.updated` then steps after `Last-Event-ID` (`id` = step index) or `?after=<step index>` (non-negative integer, given once, else 400; a valid `Last-Event-ID` wins, a malformed one reads as absent), then live events (`run.delta` of the run as `event: delta`, `data: { step, kind, text }`, **no `id:`** so `Last-Event-ID` stays a step index; live only, local replica only, never replayed); a store poll every `stream.pollMs` (2 s, on the `IClock`) covers runs executing on another replica and sends `ping` when idle; the stream ends after a settled run. A failing snapshot is an error response (500, 404 for a run gone meanwhile), never an empty 200 stream. Cleanup (unsubscribe, clear the timer, leave `ctx.closers`) runs once: on end, when `write()` returns false, or on `event.request.signal` abort (srvx aborts it on client close). `maxMessageSize` is never passed (an oversize write reads as a disconnect). Bearer auth only: browser `EventSource` cannot send `Authorization`, so browsers use a fetch-based SSE reader that sends `Authorization` and `Last-Event-ID` (or `?after=`).
- Stream cap: one counter per app (`ctx.openStreams`, cap `stream.maxOpen`, default 1000) over open SSE streams and MCP `run_<agent>` waits (`waitSeconds > 0`); `acquireStreamSlot(ctx)` (`app/helpers.ts`) returns an idempotent release or `undefined`. The stream takes its slot after the `?after` check and the shutdown 503, releases it in its one-time cleanup (end, failed write, request abort, failed snapshot or poll, shutdown); over the cap it renders `503 service_unavailable` with `Retry-After: 5` (`STREAM_RETRY_AFTER_SECONDS`) through `renderError`, not reported to `onError`. An MCP wait over the cap answers at once like `waitSeconds: 0` (the run is dispatched, never failed); a wait releases in `finally`.
- MCP: `createMcpHandler()` from `@modelcontextprotocol/server` 2.3 (stateless legacy fallback), `maxRequestBodySize: bodyLimit`; the route reads a `POST` body itself (`readBodyBytes`, same limit and drain) and hands the SDK a buffered `Request`; one `McpServer` per request whose tools depend on the principal, passed with `event.request.signal` in `authInfo.extra` (the SDK's own `ctx.http.req.signal` never aborts on disconnect). Tools: `run_<agent>` per agent with an `http.on()` subscription the principal may run, its definition (payload JSON Schema with `$ref`s re-rooted at `#/properties/payload`, compiled by `fromJsonSchema`) built once per agent object by `buildRunTool` through `createRunToolSource` (a `WeakMap`, so a replaced agent, a new object, is rebuilt; the agents held at construction eagerly, where a failure fails the app, a later one on the first request that sees it, where a failure goes to `onError` once and its tool is skipped), which throws `InvalidAgentDefinitionError` for an uncompilable schema or a name above 64 characters (channel `mcp`; `waitSeconds` clamped to `maxWaitSeconds` 60; `waitForRun` resolves on `completed | failed | cancelled | waiting` via `run.updated` or a 1 s store poll, or with the stored run on timeout or abort, signal = request signal plus `mcpReq.signal` plus the app's shutdown; ), `get_run`, `list_runs`, `approve_run` (`{ runId, approvalId, approved, reason? }`, `loadApprovableRun` then `engine.approve()`, like `POST /runs/:id/approve`). Tool failures are `isError` results; non-HTTP, non-core errors go to `onError`. Idempotency scopes differ per transport and principal (`<agent>:mcp:<kind>:<id>` vs `<agent>:http:<kind>:<id>`, see Intake).
- Extra routes (`routes: HttpRoute[]`, `routes/module.ts`): the extension point other packages plug into (`@chamvi/ui`'s dashboard) without routup in their types; run intake belongs in a channel on the mount, not here. `HttpRoute { method, path, rateLimit?: false, handler(request, ctx) }`; the handler gets `{ request, readBody() }` (`request` a body-less copy with URL, method, headers and signal, so the limited path is the only way to the body; `readBody` = content-length check plus `readBodyBytes` with the JSON media type rule: 413, 415, raw bytes, memoized per request) and `HttpRouteContext { engine, agents, clock, onError }`, and returns `{ status, body? }` (`null` sent for a missing body, since routup hangs on `undefined`). Not authenticated by the app's authenticators; thrown errors render like any route's. `buildContext` refuses (`InvalidAgentDefinitionError`) a path without a leading `/`, with `:`, `*` or `{`, a duplicate method and path, a first segment in `RESERVED_ROUTE_SEGMENTS` (`app/constants.ts`) and the metrics path when metrics are on, all compared lower-cased because routup matches paths case-insensitively (`plugins/helpers.ts` lower-cases the request path the same way for the limiter skips, the stream check and `routeLabel()`). `rateLimit: false` routes skip the limiter; `routeLabel()` labels each route by its path. A string `body` is sent as `text/plain`, a `Uint8Array` as is (a `Response` built from `event.response.headers` like the artifact route, `application/octet-stream` unless the result's `headers` name a `content-type`), everything else but `null` as JSON; `HttpRouteResult.headers` are set on `event.response.headers` first, so a `content-type` there wins. `HttpRoute.prefix: true` registers `path` and `${path}{/*rest}` (routup's optional-group syntax, as the channel mount) and hands `HttpRouteRequest.subpath` (`routeSubpath()`, `routes/helpers.ts`: the raw, percent-encoded rest of the URL pathname after `basePath` and `path`, case kept, `''` for the path itself and for a plain route); `validateRoutes` also refuses a route of the same method at or under a prefix route (lower-cased) and a prefix route at or above the metrics path; `isUnlimitedRoute` and `routeLabel` (which takes the routes, labelling a prefix route `<path>/*`) match a prefix route on `path` and below `path/`. `HttpRouteContext.basePath` is the app's `basePath` (`''` by default).
- Plugins, in order: `@routup/cors` only when `cors` is given; `@routup/rate-limit` 300 per 60 s keyed by `getRequestIP(event)` (honours the App's `trustProxy`; the library default would trust any `X-Forwarded-For`), skipping `OPTIONS`, `/healthz`, `/readyz` and the metrics path, rendering 429 through the error handler; `@routup/prometheus` at `/metrics` with a fresh `prom-client` `Registry` per app, skipping `GET /runs/:id/stream`, its `path` label the route template from `routeLabel()` (`plugins/helpers.ts`, unknown paths `/_unmatched`; keep it in step with new routes). The limiter runs first so a 429 is not timed. `/healthz`, `/readyz`, `/metrics`, the channel mount and the extra routes (which check their own credentials) are the only routes the app's authenticators do not guard.
- Shutdown: `createShutdown({ engine, server?, readinessDelayMs?, drainTimeoutMs?, closeTimeoutMs?, onError? })` (time from `engine.clock`); `shutdown()` is idempotent and runs: `shuttingDown` (readiness fails), wait `readinessDelayMs` (0), the `onShutdown` callbacks in the order added (`@chamvi/app` registers the `stopping` hooks first; the http app registers one that sets `ctx.closed`, ends SSE streams, aborts MCP `run_<agent>` waits (they answer with the stored run) and closes the MCP handler; new streams and MCP requests then answer 503 without `onError`), `server.close()` (not awaited yet), `engine.drain({ timeoutMs: 30 s })` (channels stopped first), then at most `closeTimeoutMs` (5 s) for the close before `server.close(true)`. With srvx pass `gracefulShutdown: false` to `serve()`.

## GitHub

`@chamvi/github` connects a GitHub App through the `github` channel (deliveries in, comments out; it absorbed `@chamvi/notify-github` in plan 026); it depends on `@octokit/core` with `plugin-paginate-rest`, `@ebec/http` and `smob`, peers on core and `ai`, and needs `@chamvi/http` only for its tests (nx stays acyclic).

## Sandbox and Coding

`@chamvi/sandbox` holds the contracts and shared rules, three providers implement them, `@chamvi/coding` adds the coding tools. Nothing in these packages throws `FatalToolError`: model input the model can correct is a core `ValidationError`, a workspace or provider failure a core `SandboxError` (`sandbox_error`), both tool errors; option misconfiguration is `InvalidAgentDefinitionError`.

- **Contracts**: `ISandboxProvider { name, create(options), collectGarbage() }`; `IWorkspace { id, info, disposed, exec(argv, { cwd?, timeoutMs?, stdin?, signal? }), readFile(path), writeFile(path, content), dispose() }`; `IExecTransport { exec(argv, { stdin?, stdout, stderr, signal }) -> { exitCode }, alive?(signal), remove() }` (`stdout`/`stderr` are `IOutputSink`s the workspace owns). `WorkspaceCreateOptions { runId, repo?, ref?, image?, env?, limits?, signal? }` (`repo` already normalized). No `git` method: git is `exec(['git', ...])`. Workspace ids are `randomUUID()`, so `chamvi-ws-<id>` is a valid container name, pod name and label value. A provider builds `WorkspaceInfo { runId, provider, repo?, ref?, createdAt, expiresAt }`, calls `prepareWorkspace(workspace, { repo, ref, signal })` and sets `info.commit`; a failed checkout disposes the workspace.
- **Rules** (every provider): exec takes argv only (`readonly string[]`, non-empty, no NUL); the only shell is the coding `bash` tool's `['sh', '-c', command]` inside the workspace. Paths (`resolveWorkspacePath`) are relative to the root or under `/workspace/`, the model always sees `/workspace`; empty, NUL, other absolute paths and escapes are `ValidationError` before any filesystem or exec call. Output is capped per stream at `OUTPUT_MAX_BYTES` 65 536 (`createOutputCollector`: drains past the cap, holds at most the cap, a cut UTF-8 character dropped) with `stdoutTruncated`/`stderrTruncated`. Files are UTF-8 of at most `FILE_MAX_BYTES` 1 MiB; `readFile` decodes strictly (`decodeUtf8File`), a file that is not valid UTF-8 is a `SandboxError`. Exec timeout default `EXEC_TIMEOUT_MS` 300 s, max `EXEC_TIMEOUT_MAX_MS` 1800 s, never past `expiresAt`; `timedOut` is a result. A command that cannot start exits 127.
- **Repositories** (`normalizeRepo`): `owner/name` -> `https://github.com/owner/name.git`, an https URL without credentials, query or fragment, `file:///abs` only with `allowFileRepos`; `allowRepo(url)` narrows; the `ValidationError` never echoes the input. Refs (`assertGitRef`): `^[A-Za-z0-9][A-Za-z0-9._/+-]{0,254}$` without `..`, `//`, `@{`, `/.`, a trailing `/` or `.`, `.lock`. Checkout (`checkoutCommands`, same on every provider, through the workspace's own exec): `git init -q .`, `git remote add origin <url>`, `git -c credential.helper= fetch -q --depth 1 origin <ref or HEAD>`, `git -c advice.detachedHead=false checkout -q FETCH_HEAD`, `git rev-parse HEAD`; repo-less workspaces only `git init`. A failed step is a `SandboxError` with the first 2000 characters of git's stderr.
- **Environment and limits**: containers and pods get only `SANDBOX_ENV` (`HOME=/tmp`, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `safe.directory=/workspace` via `GIT_CONFIG_COUNT/KEY_0/VALUE_0`, `NPM_CONFIG_UPDATE_NOTIFIER=false`, `CI=true`) plus the configured `env` (`assertSandboxEnv`: keys `^[A-Za-z_][A-Za-z0-9_]*$`, no NUL); local gets the host `PATH`, `HOME`/`TMPDIR` in its folder and the same git settings minus `safe.directory`. `DEFAULT_LIMITS` `cpu '1'`, `memory '2Gi'`, `storage '4Gi'`, `pids 512`, `timeoutMs 1_800_000` (`resolveLimits` merges layers over them, Kubernetes quantities); `/tmp` is a `TMP_SIZE` 512 MiB tmpfs. Labels `SANDBOX_LABELS` (`app.kubernetes.io/managed-by=chamvi`, `app.kubernetes.io/component=sandbox`), `chamvi.dev/run`, `chamvi.dev/workspace`; expiry `chamvi.dev/expires-at` (epoch ms; a Docker label, a k8s annotation). No agent label (names may exceed 63 characters).
- **Remote workspaces** (`createRemoteWorkspace`, Docker and k8s): argv wrapped as `timeout -k 5 <s> ...` (`wrapTimeout`; GNU `timeout` signals its process group) inside `EXEC_SCRIPT` (`sh -c` with a fresh marker `chamvi-exit-<32 hex>:` and the cwd made absolute under `/workspace`): the script enters the cwd (else prints `<marker>cwd` and the exec rejects `SandboxError('cwd /workspace/<p> is no directory in the workspace.')`, as on local), runs the command and prints `<marker><status>` on stderr. The workspace owns the output collectors and cuts the marker out of stderr (`createExitMarkerFilter`, also split across chunks); `EXIT_DRAIN_MS` 2 s after the marker it settles with that exit code and the output so far and detaches the transport, so a background job holding the output (`node server.js & echo started`) never stalls an exec, on Docker (whose daemon drains 2 s too) and k8s (whose exec status waits for every pipe writer). A client-side guard at timeout + `EXEC_GRACE_MS` 15 s (exit 137, `timedOut`, the output so far); `timedOut` also for exit 124/137 once the timeout passed (`isTimeoutExit`). `readFile` is `cat -- <abs>` capped at `FILE_MAX_BYTES + 1`, `writeFile` `sh -c WRITE_FILE_SCRIPT` with the bytes on stdin (`mkdir -p`, then `head -c <bytes>` into `.chamvi-write-<16 hex>` next to the file, `cp -p` first to keep an existing file's mode, then `mv -f` over it, so a concurrent reader or writer never sees a cut file; a symbolic link or a directory that takes no new file is written in place; no stdin EOF needed, so k8s `v4` works). Abort detaches (the transport drops the stream); dispose rejects every in-flight exec with `SandboxError('workspace disposed')`, then `transport.remove()` (retried on a later dispose after a failure). A failed exec asks the optional `transport.alive(signal)` (bounded by `ALIVE_PROBE_TIMEOUT_MS` 5 s; a rejection or no answer reads as alive): `false` (Docker: inspect 404 or `State.Running` false; k8s: read 404, a `deletionTimestamp`, or `podState` failed) marks the workspace gone, so `IWorkspace.disposed` reads true and every call rejects with "workspace <id> is gone ...; call create_workspace for a new one" (local: its directory missing, checked when a cwd or file is missing and before every write).
- **Providers**: `createLocalSandbox({ root?, env?, limits: { timeoutMs }?, clock? })` (`<root>/<id>/{workspace.json,home,tmp,repo}`, `writeFile` through a temporary `.chamvi-write-<hex>` file with the old mode and a `rename`, like the remote script; file paths and the cwd resolved with `realpath` before each call and refused (`ValidationError`) when they leave the root through a symbolic link or pass a dangling one (remote providers need no check: a link resolves inside the container), spawn with `detached: true`, timeout/abort/dispose kill the group with `SIGKILL`, the kill timer cleared on exit, `KILL_GRACE_MS` before closing pipes a leaver holds; a command that exited while a background job holds its pipes settles `KILL_GRACE_MS` after its `exit` with its own code and `timedOut: false`, and its group is remembered at the exit while a member still runs (also with redirected output), dropped once `process.kill(-pgid, 0)` fails (checked every `LINGER_CHECK_MS` 1 s, so a reused group id is not killed) and killed on dispose, matching Docker and k8s; no isolation). `createDockerSandbox({ docker?, image?, network?, pull?, env?, limits?, clock? })`: container `chamvi-ws-<id>`, `Cmd: sleep <lifetime>`, `User 1000:1000`, `ReadonlyRootfs`, `CapDrop ALL`, `no-new-privileges`, `PidsLimit`, `Memory` = `MemorySwap`, `NanoCpus`, `/tmp` tmpfs `rw,exec,nosuid,nodev` (Docker adds `noexec` unless `exec` is given; npm's global bins and corepack live there, like k8s' memory emptyDir), an anonymous `/workspace` volume removed with `{ force: true, v: true }`; `pull` `'missing'` (pull once on a 404), `'always'`, `'never'`; the create's `signal` is passed to the pull (the progress stream destroyed), the container create (a container made anyway removed by name) and the start; `network` default `bridge`, `none` allowed (repo-less only); storage not enforced. `createKubernetesSandbox({ namespace, kubeConfig?, image?, env?, limits?, podLabels?, imagePullPolicy?, startTimeoutMs?, pollMs?, clock?, client? })`: a bare pod (`restartPolicy: Never`, `activeDeadlineSeconds`, `automountServiceAccountToken: false`, `enableServiceLinks: false`, non-root 1000, seccomp `RuntimeDefault`, read-only root, caps dropped, requests = limits incl. `ephemeral-storage`, emptyDir `/workspace` with `sizeLimit`, memory emptyDir `/tmp`), `podLabels` may not name a managed label; `create` polls the pod on the `IClock` every `POLL_MS` up to `START_TIMEOUT_MS` (120 s) and fails fast on `FATAL_WAITING_REASONS`; `IPodClient` wraps `CoreV1Api` and `Exec` (stdin closed only on `v5.channel.k8s.io`); pids via the kubelet's `podPidsLimit`. RBAC: `pods` create/get/list/delete, `pods/exec` get and create. All three run `describeWorkspaceContract`.
- **Garbage collection**: `provider.collectGarbage()` deletes that provider's expired workspaces (local: folders whose `workspace.json` expired; Docker: containers with the managed labels past `expires-at`; k8s: pods past the annotation or in phase `Failed`/`Succeeded`), disposing open ones of the process first. A removal that fails never stops the pass: the rest go on, and one `SandboxError` (`collectionError()`, the count and the first message, every failure in an `AggregateError` cause) is thrown at the end. Docker and k8s workspaces also stop themselves at expiry (`sleep`, `activeDeadlineSeconds`).
- **Manager** (`createWorkspaceManager({ provider, image?, env?, limits?, allowFileRepos?, allowRepo?, maxWorkspacesPerRun?, gcIntervalMs?, clock?, onError? })`): workspaces keyed by `(runId, normalized repo or '')`; `acquire(runId, { repo?, ref?, signal? })` shares one create per key (`reused`), refuses another ref of a held repo and more than `MAX_WORKSPACES_PER_RUN` 3 (pending creates count) with `SandboxError`; `get(runId, id?)` (the run's only live workspace without an id, `ValidationError` for several) disposes expired and gone (`workspace.disposed`) ones and answers "not found" for an id of another run; `acquire` drops an expired or gone workspace and creates anew; `release(runId, id?)`; `attach(engine)` disposes a run's workspaces on `run.updated` with `completed | failed | cancelled` (kept while `waiting` or `interrupted`); `collectGarbage()` disposes its own expired workspaces, then calls the provider's (started by `acquire` at most every `GC_INTERVAL_MS` 10 min, `0` disables); `close({ timeoutMs? })` unsubscribes, aborts the creates in flight (each create gets the caller's signal combined with a per-entry abort) and disposes everything, waiting for both, for every disposal started earlier (a run that settled during `engine.drain()`, an expired or gone workspace; the manager tracks each) and for every create in flight a settled run's release aborted (the provider's abort cleanup, or the dispose of a workspace created anyway; reported as `a workspace of run <id> still being created`) at most `CLOSE_TIMEOUT_MS` 30 s, then reports what is still being disposed to `onError` and resolves (call after `engine.drain()`); `release(runId)` aborts and waits for the run's creates in flight too; afterwards `acquire` rejects. A workspace created while its run was released is disposed. Workspaces live in one process: a run resumed elsewhere gets "not found, call create_workspace again" (re-attach by label is plan 020).
- **Context and module**: `provideSandboxContext(engine, manager)` / `injectSandboxContext(ctx)` (key `sandbox`) in the main entry, so a tools factory builds `manager.tools()` and `codingTools(manager)` per execution. `sandboxModule()` on `@chamvi/sandbox/module` picks the provider (`CHAMVI_SANDBOX_PROVIDER`, else the option, else `local`), builds `.manager` when called, imports the provider package in `setup` by variable specifier (`SANDBOX_PROVIDER_PACKAGES[name]`, structural types: a literal import would make `build:types` need the provider's `dist`, a build cycle since every provider peers on `@chamvi/sandbox`; the providers are in none of sandbox's dependency fields, not even as optional peers or a devDependency, since release-please's graph would close `sandbox <-> provider`: the import resolves from the installed tree (npm and pnpm's default hoisting; under Yarn PnP or pnpm `hoist=false` pass `options.provider`), and the module spec loads sandbox-local through its source alias; `isPackageNotFound` is a local copy), and its hooks attach the manager and provide it (`engineCreated`) and `detach()`/`close()` it after the drain; migrate mode does nothing.
- **Tools**: `manager.tools()` = `create_workspace { repo?, ref? }` -> `{ workspace, root: '/workspace', repo, ref, commit, expiresAt, reused }` and `dispose_workspace { workspace? }`. `codingTools(manager)` (needs only `get`) = `read_file`, `write_file`, `edit_file`, `grep`, `list_files` (both `git --literal-pathspecs`, tracked plus untracked, not ignored), `bash` (`sh -c` with `cwd?`, `timeoutMs?`, returns the `ExecResult`), `git_diff` (`status --short` plus the diff, `staged?`); each takes an optional `workspace` id resolved with `context.run.runId`; camelCase result keys. All are plain `defineTool()` tools, **not effect tools**: a workspace dies with its process while an effect record survives, so a redone step on a fresh workspace would skip a recorded write, and two identical `bash` calls of one step would merge; re-applying is safe (`write_file` idempotent, `edit_file` fails with "oldString not found", `bash` in a disposable sandbox, nothing outside the workspace changes).
- **Coding backend**: `ICodingBackend { code({ workspace, task, budget?, signal? }): Promise<{ status: 'done' | 'stuck', summary, diff }> }`, contract only (own-tools backend: plan 019; Claude Code: plan 014).
- **Security model**: local isolates nothing. Docker and k8s are a code-execution boundary, not a network boundary: on `bridge` a workspace reaches the host gateway, other containers and cloud metadata, on k8s every cluster service, until 011's NetworkPolicy (select `app.kubernetes.io/component=sandbox`, deny all egress but GitHub and npm, deny the chamvi namespace and metadata) or a host firewall. Docker socket access is root on the host (socket proxy or rootless Docker). No credentials in URLs, `credential.helper` reset, no host or chamvi environment, no service account token.
- **Image**: `images/sandbox-node` (`node:24-trixie-slim` + git, ca-certificates, tini; uid 1000; npm cache, prefix and corepack under `/tmp`), `ghcr.io/chamvi/sandbox-node` tags `24` and `24-<short sha>` (the latter only on a push to `master`, so a scheduled or manual rebuild never moves it; Dependabot ignores Node.js majors), `linux/amd64` + `linux/arm64`, built by `.github/workflows/images.yml` (smoke test on PRs touching `images/**`, pushed through `tada5hi/craneship` on `master` and weekly). `DEFAULT_SANDBOX_IMAGE = 'ghcr.io/chamvi/sandbox-node:24'`; pin a digest in production.

## OpenClaw Channel

`openclawChannel({ name?, baseUrl, hooksToken, hooksPath?, agentId?, deliver: { channel, to, accountId? }, approvalUrl?, timeoutMs?, clock?, fetch? })` (`@chamvi/channel-openclaw`, the former `@chamvi/notify-openclaw`, global `fetch`, no runtime dependencies) is out only, default name `openclaw`, `defaultAddress` `deliver.to` (a tool may leave the address out). `out(message, address)`: `POST <baseUrl><hooksPath>/agent` (default `/hooks`, trailing slashes dropped, a base path kept; a `hooksToken` that is no valid header value, i.e. control characters, characters above U+00FF or surrounding whitespace, is `InvalidAgentDefinitionError`), `Authorization: Bearer <hooksToken>`, `Idempotency-Key` = `message.key`, or `sha256:<hex>` when it is over 256 characters or not visible ASCII (`transportKey`; OpenClaw silently ignores a longer key), body `{ message, name: 'chamvi', agentId?, deliver: true, channel, to, accountId? }` with `to` the address, or `deliver.to` for an empty one. The message is deterministic (no clock value or random id; OpenClaw starts a new run for a changed body under the same key): a relay instruction, title (when given), body cut to `MESSAGE_BODY_MAX_LENGTH` 8 000 (`cutText`: never ends on a high surrogate, appends `… (cut, <n> more characters)`), `Agent`/`Run`, and for an approval `Expires` and `Approve or deny: <approvalUrl({ runId, approvalId, agent })>`, else `APPROVAL_HINT`. `resumeTool` is gone: no message carries an MCP call, so OpenClaw's MCP principal needs only `agent:<name>:run` and never `agent:<name>:approve`; approval links carry ids only (suggested `https://<app>/ui/approvals?run=<runId>&approval=<approvalId>`, the signed-in owner answers through `POST /runs/:id/approve`). Any 2xx resolves; otherwise `OpenClaw <status>: <text>` (`(retry after <v>)` for `Retry-After`), `OpenClaw request failed: <message> (<cause message>)`, `OpenClaw did not answer within <ms>ms.` (code `openclaw_request`), bounded by `timeoutMs` (30 s) on the `IClock`; the response text has `hooksToken` replaced by `[redacted]`, then is cut to 500 characters. `openclawModule()` (`@chamvi/channel-openclaw/module`, module name `chamvi:channel:<name>`) reads `OPENCLAW_*` env, links approvals from `CHAMVI_PUBLIC_URL` and contributes the channel to `AppToken.CHANNELS`; tools use `ctx.channels.findOne(name)` (the context pair is gone). Verified OpenClaw facts (2026-10-21): hooks off by default, `channel: 'last'` and partial destinations are 400, bodies over 256 KiB 413, `200 { ok, runId }` means admitted (not delivered), replay entries live in memory for 5 minutes after completion and a restart clears them, so chamvi's records (the emit effect, `waiting.notifiedAt`) are the primary dedupe. OpenClaw runs an agent turn on the message and treats it as external content.

## Web Tools

`@chamvi/tool-web` holds `webTools({ client?, lookup?, allowUrl?, maxBytes?, timeoutMs?, clock? })`, one plain `defineTool()` tool, `web_fetch`, that runs in the chamvi process; it peers on core and `ai` and depends on `hapic` (requests and proxy), `turndown` with `@mixmark-io/domino` (HTML to markdown) and `smob`. Options are checked when called (`InvalidAgentDefinitionError`).

- **Request** (`getPage()`, `tools/asserts.ts`): a GET through the hapic client (default `createClient()`, whose `FetchTransport` takes the proxy from `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`) with `redirect: 'manual'` and `responseType: 'stream'`; redirects followed by hand (at most `WEB_MAX_REDIRECTS` 5); before every hop `parseWebUrl` (http(s) only, no credentials, `ValidationError`) and `checkUrl` (`allowUrl(url)`: `true` allows, `false` refuses, `undefined` resolves the host through `lookup` (default `dns.lookup`, every address) and refuses a host with any address `isBlockedAddress()` holds, `ValidationError`); the body read up to `maxBytes` (default `WEB_FETCH_MAX_BYTES` 5 MiB, the rest cancelled, `truncated`); `timeoutMs` (default `WEB_TIMEOUT_MS` 30 s) on the `IClock` over the whole fetch; a 4xx/5xx status, a network failure and the timeout are `ChamviError`s with code `web_request` (`WEB_REQUEST_ERROR_CODE`), tool errors. The request resolves the name again, so DNS rebinding and a proxy's own connect are not covered (documented; an egress policy is the operator's tool).
- **Address check** (`address/`): `parseAddress()` (IPv4/IPv6 to bytes, brackets and a trailing dotted quad allowed), `isBlockedAddress()` over `BLOCKED_IPV4`/`BLOCKED_IPV6` (this network, RFC 1918, CGNAT, loopback, link-local and metadata, multicast, reserved, documentation, benchmarking; IPv4-mapped, NAT64 and 6to4 judged by the IPv4 inside; anything that is no IP address is blocked).
- **`web_fetch({ url, format?, offset? })`** (`tools/fetch.ts`): a type that is no text (`isText`: `text/*`, JSON, XML, scripts, `+json`/`+xml`, none) is a `web_request` error; the body decoded by its charset (or `<meta charset>`, else UTF-8); an HTML page converted inline (no worker) to markdown (`htmlToMarkdown`, links absolute) or text (`htmlToText`), at most `HTML_MAX_CHARS` 1 Mi characters of it (`truncated`); `raw` returns the body; at most `WEB_FETCH_MAX_CHARS` 65 536 characters from `offset` (never inside a surrogate pair, an offset past the end a `ValidationError`), `nextOffset` while more follows. Package registries are plain JSON URLs the description names (`https://registry.npmjs.org/<name>`, `https://pypi.org/pypi/<name>/json`); there is no registry or search tool.

## App and CLI

`@chamvi/app` (library, no process concerns) turns `export default createApp({ agents, modules?, models? })` into a running app; `@chamvi/cli` (bin `chamvi`, citty only) adds argv, entry loading, signals and exit codes. Contract: `.agents/plans/011-deploy-kit.md` C1 to C5 while it lives.

- **App**: `createApp()` is synchronous and side-effect free (refuses options that are no object or an `agents` that is no array (no agents at all is allowed: `chamvi:agents` logs `NO_AGENTS_MESSAGE` as a warning when there is no agents dir either), a `modules` entry that is no `IModule` object, since orkos would `import()` a string, and a name used twice, a built-in's included) and branded (`APP_BRAND`, `isApp()` matches another installed copy). Each lifecycle (`start({ env?, dev? })`, `runJob({ agent, subscription?, env? })`, `migrate({ env? })`) builds one orkos `Application` over a fresh eldin `Container` with `AppToken.CONTEXT` (`mode` `start`/`job`/`migrate`, `dev`, `env`, the stop `signal`, `report`, `models`, `agents`) registered first; an app runs one lifecycle (`app_in_use` after it, also after `stop()`). orkos graph errors (a dependency the app does not register, a cycle, a version mismatch) become `InvalidAgentDefinitionError` (`toSetupError()`). `stop()` is memoized: it aborts the context signal (`app_stopped`), waits for the lifecycle in flight, tears down; a setup error answered by `app_stopped` is logged, never lost; every teardown error is reported (orkos swallows them, `reportingModule()`) and `stop()` (or a job's teardown) then rejects with `app_stop_failed`. A module whose `setup` throws is never torn down by orkos, so each destroys its own partial state first; one whose `onReady` threw is, so every `teardown` tolerates half-built state.
- **Modules**: built-ins in order `chamvi:config`, `chamvi:store`, `chamvi:static-tokens`, `chamvi:engine`, `chamvi:agents`, `chamvi:scheduler`, `chamvi:http` (`ModuleName`), each replaced in place by a user module of the same name, then the user modules. `setup` contributes to the collection tokens (`HTTP_ROUTES`, `CHANNELS` (every `IChannel` the engine registers: the scheduler module's `cron` channel, the http module's `http`, `mcp` and `webhook`, `consoleChannelModule()`'s, the feature modules'; names unique, a clash fails the setup with `InvalidAgentDefinitionError`), `AUTHENTICATORS` with an `order`, `LIFECYCLE_HOOKS`); `onReady` consumes (engine: channels; http: authenticators, routes, every contributed channel with an `in` for `createHttpApp({ channels })`), so contributions need no order; a module resolving `ENGINE` or `SERVER` in `onReady` lists it in `dependencies`. Start steps (`module/start.ts`, internal): the engine module registers `engine.start()` in `onReady` (job mode: `runJob` starts it with `channels: false`); the app runs the steps once every `onReady` ran (user modules included): `engine.start()` (recovery, then every channel's `start`), then the http module's serve step (the `started` hooks, i.e. the purge timer, then `serve()` and `ready()`); without the http module the app runs the `started` hooks itself and the `stopping` hooks before the teardown. So a configuration error found in any `onReady` starts nothing and executes no queued run of the shared store. Hooks: `engineCreated` (start and job), `started`, `stopping` (first in the shutdown, before the drain stops the channels), `drained` (after the engine drained, before the store closes); a throwing hook is reported, the others run. The static-tokens module contributes `CHAMVI_TOKENS` in `setup` and, in dev without any other authenticator, a random `*` token (id `dev`, logged once) in `onReady`; http lists it as an optional dependency. Optional modules live in the feature packages on a `/module` subpath (`@chamvi/github/module` `githubModule`, `@chamvi/channel-openclaw/module` `openclawModule`, `@chamvi/sandbox/module` `sandboxModule`, `@chamvi/ui/module` `uiModule`; `@chamvi/app` an optional peer there, `src/module/` the only folder importing it, kept external in `dist/module.mjs` so one `AppToken` set exists per process) and contribute their channel to `CHANNELS` or provide their instance in the `engineCreated` hook through the package's context pair; a throwing `engineCreated` hook (e.g. a second provide of one key) is caught by `runHooks` and reported through `context.report()`, the app still starts. `@chamvi/app` keeps only `/authup` (`authupModule`, `oidcModule`: moving them to `@chamvi/http` would make http depend on app, a cycle) and `/testing` (`buildModuleHarness()`/`createModuleHarness()`: the real lifecycle over the given modules, `reportingModule` and `runStartSteps` included, `reported` collecting `context.report()`), and its main entry exports the module contract (`AppToken`, `ModuleName`, `AppContext`, `ILifecycleHook`, env readers, `approvalUrlOf`, the orkos `IModule` and eldin `IContainer` types). No `@chamvi/*` feature package is in any of its dependency fields. nx 23.3 and release-please's node-workspace plugin (17.x, `updatePeerDependencies: true`) both read the package.json graph: nx turns dev and peer dependencies into static edges, release-please takes dependencies, devDependencies, optionalDependencies and peerDependencies, and a cycle aborts the whole release run (`found cycle in dependency graph`, nx exclusions do not reach it). So the graph is acyclic in all four fields, without `nx.implicitDependencies` exclusions: `@chamvi/test-kit` does not depend on `@chamvi/sandbox` (its workspace contract types `IWorkspace` structurally), which would close `sandbox -> app -> ... -> test-kit -> sandbox`, and `@chamvi/sandbox` names no provider package. `packages/app/test/unit/graph.spec.ts` pins it from `release-please-config.json`. Optional modules read `options.env ?? process.env` and check their options when the factory is called (errors name the variable, never echo a value, also for the values `createGithubApp()` and `openclawChannel()` refuse) and expose their instance synchronously.
- **Config and env** (`readConfig(env, { mode, dev })`, `env/`): empty is unset, integers `/^\d+$/` and every `*_MS` at most `TIMER_MAX_MS` (2^31 - 1, a larger Node timer fires after 1 ms), booleans `true|false|1|0`; every error names the variable and never its value. `DATABASE_URL` builds a `DataSource` (`STORE_ENTITIES`, `STORE_MIGRATIONS`, `connectTimeoutMS` `STORE_CONNECT_TIMEOUT_MS` 10 s, password masked in place in every error), migrated in migrate mode or with `CHAMVI_MIGRATE`; without it a `MemoryStore` (warned outside dev); `purgeExpired()` hourly in start mode. Model strings `'<provider>/<model>'` resolve through an AI SDK provider registry of the installed built-in providers and their env keys (`createModelRegistry()`, overridden by `models`), checked at `start`/`runJob` (missing package or key: `InvalidAgentDefinitionError`) and installed as `globalThis.AI_SDK_DEFAULT_PROVIDER` only when none is set.
- **Agent folders** (plan 025a; `loader/`, `modules/agents/`): `CHAMVI_AGENTS_DIR` (optional, relative to the cwd; unset, `AgentsModule.setup` takes `./agents` (`DEFAULT_AGENTS_DIR`) when it is a directory, and an explicitly named dir that is none fails `onReady`) and `CHAMVI_AGENTS_POLL_MS` (`DEFAULT_AGENTS_POLL_MS` 5000, 1 to `TIMER_MAX_MS`) in `AppConfig.agents`. Layout `<dir>/<name>/agent.ts` and nothing else enforced (owner decision 2026-10-22; folder name = agent name, `.`/`_`-prefixed folders skipped): `agent.ts` default-exports `defineAgent()`'s result, checked structurally (`name` a string, `definition` an object) so another core copy's agent passes; its `name` must equal the folder name (a missing `agent.ts` is `<name>: has no agent.ts.`, no `.mts`/`.js`/`.mjs` variant), and its `definition` is re-run through this copy's `defineAgent()`. The rest of the folder is the user's: `agent.ts` loads its tools, instructions, subscriptions and helpers with plain imports or reads (`readFileSync(new URL('./prompt.md', import.meta.url))`). `agent.ts` loads through one `jiti` (`moduleCache: false`, `fsCache: false`, `createModuleJiti()`, `readFreshModule()`): `readModule()` evaluates it with `evalModule(source, { forceTranspile: true })`, and its relative `.ts`/`.mts` imports transpile fresh too; a JavaScript file anywhere in the folder (`.js`/`.mjs`/`.cjs`, `assertNoScripts`, checked before any load) is a load error, since Node's native import cache never forgets one; required JSON is dropped from the CommonJS cache after each read. `createPackageAliases()` pins `@chamvi/*`, `ai` and `@ai-sdk/*` (every non-wildcard exported subpath, ESM conditions, closest `node_modules` of `@chamvi/app` first) as jiti aliases, so an agents dir anywhere (a volume outside the app) gets the app's instances; packages load natively. A `node_modules` folder in an agent folder or the agents dir is a load error (a second copy). `test/unit/loader/identity.spec.ts` pins a module-provided context key injected by a tool `agent.ts` imports, on the built packages (so nx runs the app's tests after its build). `locter` (`locateMany`, folder discovery and hashing) and `jiti` are dependencies of `@chamvi/app` only. `hashAgentFolder` = sha256 hex over every file (dot-entries skipped) by relative POSIX path, `path\0bytes\0`, taken before and after the read (a difference is `changed while loading`). `loadAgent` throws `InvalidAgentDefinitionError` naming files relative to the agents dir; `loadAgents` returns `issues`. `AgentsModule` (depends on config and engine): `setup` resolves the dir (`this.root`) and, without one, only warns for an app without code agents (`NO_AGENTS_MESSAGE`), else registers `AGENT_ISSUES` and, in start mode, the lifecycle hook `chamvi:agents-watcher` (`started` starts, `stopping` stops); `onReady` (start and job) checks the dir (`NO_DIRECTORY_MESSAGE`) and boots the watcher: every folder loaded and `putAgent(agent, { revision: hash })`, checked by `MODEL_CHECK` (the engine module's `resolveModels().check`, a no-op with a preset default provider), then (start mode only, never a job) every marker with neither a folder nor a code agent removed; all before the start steps. Before `putAgent` a folder agent passes the `check`: `MODEL_CHECK` and every `AGENT_CHECKS` contribution (scheduler: `assertSchedulable`; http: `assertMcpRunTool` unless `mcp: false`; both in start and job mode), and an `InvalidAgentDefinitionError` from `putAgent` itself (a subscription to an unknown channel, thrown before any store write) is an issue too, so nothing a later consumer refuses crashes the boot or cancels runs; the cron channel and `createRunToolSource` report a folder agent's failure to `onError` instead of throwing. A load is registered only when it read exactly the poll's stable hash (else `unstable`: nothing recorded, the next stable poll decides; the boot retries `BOOT_LOAD_ATTEMPTS` 3 times). Every poll reads the markers once and records an applied agent whose marker another process moved or removed while its folder is unchanged as an issue (logged `agent revision moved`), without re-syncing. The watcher (`createAgentsWatcher`, internal) polls on the `IClock` (`keepAlive: false`): a folder whose hash differs from the last attempted one loads once two consecutive polls see the same hash, a broken folder is tried once per content (an issue `{ agent, message, at }` logged `agent load failed`, the previous agent kept, no marker written), a folder missing on two polls is removed, a missing agents dir removes nothing, a store failure retries on a later poll; a folder named like a code agent is an issue, never loaded or removed (code wins). `AGENT_ISSUES` reaches `createHttpApp({ agentIssues })` and the UI's agents page notice.
- **Stop order** (C5): `createShutdown().shutdown()` (readiness 503, `CHAMVI_READINESS_DELAY_MS`, the `stopping` hooks, closers, `server.close()`, `engine.drain()` (every channel's `stop()` first, the cron schedule among them), the close timeout), then the engine module's `drained` hooks (sandbox: `detach()` and `manager.close()`), then the store's `dataSource.destroy()`.
- **CLI**: commands `dev`, `build`, `start`, `run-job`, `migrate`; exit codes `0` success, `1` runtime failure or forced exit, `2` usage or configuration (citty's `CLIError`, `cli_usage`, `invalid_agent_definition`; `exitCodeOf()` takes the codes from `@chamvi/app`). The entry is `--entry <path>` (a bare one is exit 2), else `chamvi.entry` (source commands only), else `src/index.ts` or `dist/index.mjs`; with none of them `resolveEntry()` is `undefined` and `loadEntryApp()` builds the default app `createApp({})` (agents from `./agents` or `CHAMVI_AGENTS_DIR`, `DEFAULT_APP_NOTICE` on stderr), `dev` spawns `start --dev` without `--entry`, `build` exits 2 (nothing to build); a missing `dist/index.mjs` beside a `src/index.ts` keeps the build hint. Signals (`installSignalHandlers()`): the first SIGTERM/SIGINT stops (exit 0, or 1 when the stop failed); a repeat within `SIGNAL_REPEAT_MS` (1 s) is the same signal (npm forwards SIGINT while the terminal signals the group); a later one exits 1; `CHAMVI_FORCE_EXIT_MS` (90 s, dev 15 s) after the first exits 1, on a kept-alive timer cleared once the stop settled. `run-job` keeps the job's code over the stop's (a failed run stays 1 after a signal) and prints `<agent>: <status> (run <id>)`. `dev` spawns `node --watch [--env-file-if-exists=.env] <cli> start --dev --entry <src>` detached (the env flag only when `.env` exists at start; Linux `node --watch` fails with ENOENT on a missing env file) (one forwarded signal per signal; SIGHUP and the CLI's exit send SIGTERM) with a stdin pipe only it writes and `CHAMVI_DEV_LINK=1`, so `start --dev` ends the whole group (`kill(-ppid)`) once the pipe closes (the CLI died by SIGKILL). `build` drives tsdown (optional peer) into `<out-dir>/index.mjs` with `clean: true`, refusing an out dir that is the project folder or above it, holds the entry, or holds anything but `.mjs`/`.mjs.map` files. `start --dev` (hidden from the usage) loads `.env` with `node:util` `parseEnv` before the entry import.

## Errors

All errors extend `ChamviError` (ebec `BaseError`) with a `code`: `InvalidAgentDefinitionError`, `BudgetExceededError` (`BudgetExceeded`), `FatalToolError`, `IncompleteResponseError` (`incomplete_response`), `ContextNotProvidedError` (`context_not_provided`, a tool error in `execute` and effect hooks, a failed run from the tools factory), `RunNotFoundError`, `ArtifactNotFoundError` (`artifact_not_found`), `InvalidRunStateError`, `LeaseLostError`, `TimeoutError` (`Timeout`), `ToolNotAllowedError` (`tool_not_allowed`, only ever a tool error), `ToolDeniedError` (`tool_denied`, a gate's refusal, only ever a tool error), `ChannelNotFoundError` (`channel_not_found`, `ctx.channels.findOneOrFail()` for an unknown channel or one without `out`, and an approval delivery through a channel the engine no longer has, to `onError`), `AgentNotFoundError` (`agent_not_found`, `dispatch` for an agent the engine does not hold, http 404), `SandboxError` (`sandbox_error`, a workspace or provider failure, only ever a tool error), `ValidationError`; the codes are `ErrorCode` (`errors/constants.ts`); outside core three more codes exist: `github_request` (`@chamvi/github`'s tool errors, never fatal, and its channel's send failures), `openclaw_request` (`@chamvi/channel-openclaw`) and `web_request` (`@chamvi/tool-web`'s request failures, never fatal). A failed run stores `{ code, message }` in `run.error`.
