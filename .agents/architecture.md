# Architecture

## Core Concepts

App, Agent, Channel, Run, Step, State, Tool, Workspace, Store. Keep the concept surface at about ten. chamvi never wraps the AI SDK: models (`LanguageModel`), messages (`ModelMessage`) and tool sets (`ToolSet`) are passed through as-is.

`@chamvi/core` holds: agent definitions with channel subscriptions and tool hooks, the `IChannel` contract and the tool-driven outbound (`ToolContext.channels`, `consoleChannel()`), the `Engine`, step checkpoints, budgets, effect tools, durable approvals (`approve()`, answered by run and approval id), recovery and drain, agent state, streaming deltas, structured output, run artifacts (attachments and tool files), the `IStore` interfaces, `MemoryStore`. Everything time-based goes through an injectable `IClock` (`systemClock`; `ControllableClock` in tests). The public surface is `src/index.ts`. `@chamvi/test-kit` exports `describeStoreContract` and `ControllableClock`.

## Engine

`new Engine({ store, agents, ... })` validates at construction (`InvalidAgentDefinitionError`): agent and channel names unique (channel names follow the agent-name rule, `assertChannelName`), every subscription must name a registered channel (`assertRegistrable`: `Agent "<a>" subscribes to unknown channel "<c>".`), and every agent's model must resolve (see Models below). Defaults: `claimTtlMs` 60 s, `concurrencyMaxRuns` 4, `owner` `${hostname}-${pid}`, `clock` `systemClock`, `onError` logs to `console.error`. `start({ channels? })` recovers, starts every channel (see [Channels](#channels-and-the-envelope)) and begins polling; `dispatch`, `cancel`, `approve`, `tick`, `recover` and `drain` are the operations; `provide(key, value)` (`IContextProvider`) holds the values tools inject (see [Context](#context)). The engine is the one source of what an app is built from: `store` and `clock` are public readonly fields, `getAgent(name)` and `listAgents()` (registration order, a new array) read the registered agents and `getChannel(name)`/`listChannels()` the channels, so channels and `@chamvi/http` take only the engine. `on(type, listener)` is typed per event (`run.updated` carries `run`, `step.appended` carries `step`, `run.delta` carries `delta`) and sees local events only.

**Live registry** (`engine/registry/`, plan 025a): the agent set changes at runtime. `putAgent(agent, { revision? })` registers an agent or replaces the one of the same name in place (a new one goes last), refusing a subscription to an unknown channel or a model that does not resolve like the constructor (`assertRegistrable`, `checkAgentModel`), before any store write, and resolves `added | replaced | unchanged` (`unchanged`, no event, for the same object at the same revision); `removeAgent(name)` resolves whether it was registered here; `agentRevision(name)` is the revision an agent was registered at (`undefined` for a code agent). Both emit `agents.changed` (`AgentChange { name, kind: 'added' | 'replaced' | 'removed' }`, local; `EngineEvent = RunEvent | AgentChange`). Every marker operation runs under the store lock `agents:<name>` (`withAgentLock`, owner a fresh `randomUUID()` per attempt, TTL `AGENT_LOCK_TTL_MS` 300 s, retried every `claimTtlMs / 3` on the `IClock`, `InvalidRunStateError` after 300 s): with a `revision` (a folder's content hash), `syncRevision` reads the marker and, when it differs, cancels the agent's unsettled runs (`queued | running | waiting | interrupted`) created before `changedAt = now` (only when a marker existed: a first sight cancels nothing), then writes `{ agent, hash, changedAt }` (`changedAt` taken right before the write) and sweeps again for runs created before it (a replica at the old hash may create and start one until the write lands), so a change cancels once across replicas; while it syncs, this engine starts no run of the agent (`syncing`, checked by `prepareStart` and `isCurrent`); without one, replacing a registered agent cancels its unsettled runs created before now. `removeAgent` first unregisters the agent and emits `removed` (no further dispatch here), then `dropRevision` cancels all unsettled runs and deletes the marker when one exists (also for an agent this engine never loaded), unless this engine had the agent at another revision (a newer one registered elsewhere: marker and runs left alone); without a marker it cancels the runs of an agent registered here (code or folder: no replica runs it any more, so a lagging replica's runs never stay queued). Cancels run concurrently through the engine's `cancelRun(id, reason)` (a run settled or gone meanwhile is skipped, other failures go to `onError`) and store a reason as `Run.error` (`agentCancelReason()`, `registry/helpers.ts`; no error class): `agent_replaced` (`Agent "<a>" was reloaded at revision <12 hex>; its unsettled runs were cancelled.`, `REVISION_PREFIX_LENGTH` 12, or `... was replaced; ...` for a code agent) and `agent_removed` (`... was removed; ...`); a local execution keeps it on its executions entry (`cancelReason`) for `finish()`, a stored run gets it in `cancelStored`, a run on another replica with `cancelRequested` (the owner's `cancelled` settle keeps it; a `completed` settle clears `error`). `cancel(runId)` stores none. After a sweep (`syncRevision`/`dropRevision`/the code-agent replace resolve the cancelled ids, `undefined` when no sweep ran: first sight, unchanged, another revision) the engine emits `AgentRunsCancelled { type: 'agents.cancelled', name, reason, revision?, runIds }` (local, so once across replicas; also with no ids). `checkAgent(agent)` (public) throws what `putAgent` refuses before any store access (`assertRegistrable`) and registers nothing. `putAgent(agent, { revision, reload: false })` never cancels (`claimRevision`, under `agents:<name>`): a missing marker is written (nothing cancelled), an equal one kept, a different one moved only while the agent has no unsettled run, else `InvalidRunStateError` (`Agent "<a>" runs revision <stored 12> in the store, not <loaded 12>; this process does not reload agents.`) with the agent unregistered and marker and runs untouched. `formerRevision` (both modes): a marker at it (the same content under an earlier hash algorithm) counts as equal and is moved to `revision` keeping its `changedAt`, nothing cancelled (`moveFormerMarker`). `dispatch` for an agent the engine does not hold throws `AgentNotFoundError` (`agent_not_found`, http 404).

**Models** (`model/`, plan 028a): `ModelRef = string | LanguageModel`; `EngineOptions.model?: ModelRef` is the default of agents without one, `EngineOptions.models?: IModelResolver { check(ref, agent?), resolve(ref) }` resolves strings `'<provider>/<model id>'` (split at the first `/`). The constructor checks the default (`checkDefaultModel`: a non-empty string or an object, a string needs `models` and passes `models.check(ref)`), and the constructor and `putAgent` check every agent (`checkAgentModel`, public: `Agent "<a>" has no model and the app sets no default (CHAMVI_MODEL).`, a ref of another shape, a string without a resolver, a string `check` refuses; objects are never checked), each `InvalidAgentDefinitionError`. At execution start the engine takes `agent.definition.model ?? options.model`, resolves a string through `models.resolve()` (`toLanguageModel`, `model/asserts.ts`; a resolver failure is wrapped as `Model "<ref>" could not be resolved: ...`) and always hands `ToolLoopAgent` an object, so the AI SDK never sees a string and its global provider is never consulted. `resolveModel(ctx, ref?)` (public) gives tool code a `LanguageModel`: `ref`, else the run's agent model from the live registry, else the default; it reads the engine's `ModelContext { model?, models?, agentModel(name) }` provided under the internal `MODEL_CONTEXT` key (`model/constants.ts`) at construction, so `ToolContext` keeps its shape; a string without a resolver is `InvalidAgentDefinitionError` (`resolveModel(): the model string "<ref>" needs a model resolver (EngineOptions.models).`), a tool error in `execute`, and a hand-built context throws `ContextNotProvidedError`.

## Agents

`defineAgent({...})` takes a typed config object and returns `{ name, definition }` with the budget defaults applied (`maxSteps: 20`, `timeoutMs: 15 min`). `model?: ModelRef` is optional (the engine's default applies, see Models); tool code reaches a model through `resolveModel(ctx, ref?)`, never a bare string to the AI SDK. Agent names match `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 chars, unique per app; `channels: ChannelSubscription[]` (subscription ids unique per agent, `InvalidAgentDefinitionError` otherwise). `tools` is a plain `ToolSet` or a factory `(ctx: ToolContext) => ToolSet`, called per execution. `assembleTools` builds one `ToolContext { run, state, artifacts, channels }` per execution (shared by the factory and every call) and passes it as the `ToolLoopAgent`'s `toolsContext` (`as never`: a `ToolSet` infers no context type) only to tools whose `contextSchema === toolContextSchema` (`tool/`: `defineTool()`, `defineEffectTool()` and the state tools set it; `validate` returns the value by identity and rejects a non-object, which fails the run, since the AI SDK validates the context outside its tool-error handling). The agent's `toolsContext?: Record<string, unknown>` entries go unchanged (by reference, never cloned or stored) to tools that are not chamvi's (also to one without a `contextSchema`); an entry naming a chamvi tool or no tool is an `InvalidAgentDefinitionError` (`assertToolsContext`, `agent/helpers.ts`: thrown by `defineAgent` for a plain set, a failed run before any model call for a factory), and a third-party tool with a required `contextSchema` and no entry (or a rejected one) fails the run. `toRunError` turns that AI SDK `TypeValidationError` (`context.field === 'tool context'`) into a `ValidationError` naming the tool and the issue paths only, since the SDK's message (and some validators' issue messages) hold the entry's value, which may be a secret; chamvi's own missing-context issue keeps its message. `StepResult.toolsContext` is never stored (steps are built field by field). `artifacts` (`IRunArtifacts`: `put`, `get`, `list`) is scoped to the run (`get` of another run's artifact is `undefined`) and is no effect by itself (wrap `put` in `defineEffectTool` for exactly once). `output` takes an AI SDK `Output` (`Output.object({ schema })`), passed to `ToolLoopAgent` as is. `hooks: { beforeToolExecution?, afterToolExecution? }` run inside `wrapToolsForRun` for every tool of the merged set (user, chamvi, state, third-party; see [Approvals and hooks](#approvals-and-hooks)). An AI SDK tool declaring its own `needsApproval` is refused (`assertNoNeedsApproval`, `agent/helpers.ts`: `defineAgent` for a plain set, a failed run before any model call for a factory), since nothing answers that request. `toolPolicy(toolName, { run })` is applied to the merged tool set (state tools included) in `assembleTools`: the allowed names become the `ToolLoopAgent`'s `activeTools`, so a refused tool is never offered to the model, while every tool stays in `tools` so a pending call that runs after an approval (policy tightened before the resume) still reaches `wrapToolsForRun`, which re-checks every call and answers a refused one with a `ToolNotAllowedError` tool error (the run goes on). A model that calls a refused tool anyway gets the AI SDK's `NoSuchToolError` answer (the tool is not in `activeTools`); `refusedCallError()` (`execute/helpers.ts`) records that tool step as `ToolNotAllowedError` (`tool_not_allowed`), only for a tool of the full set whose invalid call carries a `NoSuchToolError`, so a genuinely unknown tool keeps the SDK's error. The policy should depend only on the run snapshot, so the tool set is stable across executions. `requireToolPermission({ withoutInvoker? })` (`permission/`) offers a tool when the invoker holds `tool:<agent>:<tool>` (`hasPermission`: `*` alone grants everything, a `*` segment matches one segment, segment counts must match; `@chamvi/http` delegates to it); runs without an invoker follow `withoutInvoker` (default `'deny'`).

### Context

`context/` (core): `defineContextKey<T>(name)` returns a frozen `ContextKey<T>`, unique per call (registered in a module-private `WeakSet`; the name is for messages only, an empty or non-string one is `InvalidAgentDefinitionError`). `engine.provide(key, value)` stores the value by reference in the engine's `Map` and refuses a foreign key, also one of another `@chamvi/core` copy a package resolved (`Context "<name>" has no key from defineContextKey() of the engine's @chamvi/core: ...`), `undefined` (`Context "<name>" needs a value.`) and a second value for one key (`Context "<name>" is already provided.`), each `InvalidAgentDefinitionError`; a value provided after `start()` reaches the next execution, since the map is read at call time. There is no `EngineOptions.context`. The engine passes the map as `ExecuteContext.provided`; `assembleTools` binds it to the execution's `ToolContext` through a module-private `WeakMap` (`bindProvided`, `context/helpers.ts`) right after building the context and **before** the tools factory runs, so `inject(ctx, key)` / `tryInject(ctx, key)` return the same object in the factory, in `execute` and in the effect hooks (`alreadyApplied`, `effectKey`). `ToolContext` is exactly `{ run, state, artifacts, channels }` (no own key for a provided value, string or symbol), and nothing provided is stored, cloned or serialized into steps, checkpoints or runs. A spread copy (`{ ...ctx }`) or a hand-built context has no binding: `inject` takes the context the engine passed. `inject` without a value throws `ContextNotProvidedError` (`context_not_provided`, naming the key only, never a value): a tool error in `execute` and in the effect hooks (they run inside the wrapped `execute` of `wrapToolsForRun`), a run failure before any model call in the factory (`assembleTools` rethrows it, `guardedExecute` settles the run `failed` and reports it to `onError`). Feature packages export a core-only pair per shared instance (`provide*Context(engine, value)`, `inject*Context(ctx)`) and keep the key internal. Channels need no pair: `ToolContext.channels` holds run-bound handles (see [Channels](#channels-and-the-envelope)); tools never get the engine itself.

## Channels and the Envelope

A channel (`channel/`, plan 026) is anything a run comes from or talks to; the presence of `start`, `in` and `out` is its only capability:

```ts
interface IChannel<TInput = ChannelRequest, TOutput = Response> {
    readonly name: string;                       // agent-name rules; unique per engine
    readonly defaultAddress?: string;            // emit()/approve() target without an address off the source channel
    start?(ctx: ChannelContext): Promise<void>;  // background intake (cron ticks, sockets, polling)
    stop?(): Promise<void>;
    in?(input: TInput, ctx: ChannelContext): Promise<TOutput>;  // HTTP: { request, subpath }, the raw Request and the raw subpath
    out?(message: ChannelMessage, address: string, opts: ChannelSendOptions): Promise<void>; // idempotent on message.key
}
// ChannelContext { engine, dispatch(envelope) }: dispatch sets `channel` to the channel's own name (createChannelContext)
// ChannelMessage { kind: 'message' | 'approval', key, runId, agent, title?, body, approvalId?, expiresAt?, options?, multiple? }
// ChannelSendOptions { signal, trigger }: trigger = the run's stored envelope, read only
```

- **Lifecycle**: `EngineOptions.channels: IChannel[]`. `engine.start()` calls every `start(ctx)` after the first `recover()`, sequentially in registration order; a throwing `start` stops the channels already started and rejects `start()`. `engine.start({ channels: false })` starts none (`runJob()`). `stop()` stops the poll and every started channel (`Promise.allSettled`, rejections to `onError`) and returns that promise, so a caller can wait for the channel stops (cron ticks in flight) before closing the store; `drain()` awaits it **first**, then drains. A non-empty `defaultAddress` is checked in the constructor (`assertDefaultAddress`, `InvalidAgentDefinitionError`).
- **Subscriptions** replace trigger definitions: `ChannelSubscription { channel, id, options, concurrencyKey?(p), idempotencyKey?(p) }` on `AgentDefinition.channels`. Each channel package exports a builder named after its default channel whose `on()` makes pure-data subscriptions (`cron.on()` in `@chamvi/channel-cron`, `http.on()`/`webhook.on()` in `@chamvi/http`, `github.on()` in `@chamvi/github`), and the channel factory's instance has `on()` bound to its own name (a second instance). Channels read their subscriptions from `ctx.engine.listAgents()` and follow `agents.changed`.
- **Outbound is tool-driven**: the engine never sends a message of its own, except the approval requests a tool asked for (see [Approvals and hooks](#approvals-and-hooks)). `ctx.channels` (`ToolChannels`, built per execution by `createToolChannels()`, `channel/helpers.ts`, over `engine.getChannel()`/`listChannels()`) hands out run-bound `ChannelHandle { name, address?, emit, approve }`s for channels with `out`: `findOne(name?)` the channel `name` (default the run's `trigger.channel`) or `undefined` when the engine has none of that name or it has no `out`; `findOneOrFail(name?)` the same or `ChannelNotFoundError` (`channel_not_found`, naming the channel only); `find()` every channel with `out` in registration order. A handle on the source channel is bound to `trigger.address`. `emit({ title?, body, key? }, address?)` and `approve({ ..., address? })` default to the source address on the source channel, else to the channel's `defaultAddress` (`consoleChannel()` its name, `openclawChannel()` its `deliver.to`), else need one (`ValidationError` tool error); `emit` and is an effect (`createChannelHandle`, `channel/helpers.ts`): key `<runId>:emit:<channel>:<sha256 of address and canonical message>` (or `key`), recorded through `IEffectStore` like `wrapToolsForRun`, and passed to `out` as `message.key`, so identical emits of one step and a step redone after a crash send once; a throwing `out` records nothing and is a tool error. Outside a tool call (the tools factory) `emit` throws `InvalidRunStateError`.
- `consoleChannel({ name?, write? })` (`channel/console.ts`): out only, default name `console` (also its `defaultAddress`), one header line `[chamvi] <kind>: <title ?? the body's first line> (agent <a>, run <r>, key <k>)`, the body lines, for an approval with options `select one:` (or `select one or more:`) and an `option <id>: <label>` line per option, then `approval <approvalId> waits until <ISO>`; never throws.
- **Hand-offs** (`handoff/`, plan 031c): `startHandoff(ctx, { payload, idempotencyKey?, concurrencyKey?, address? })` (a free function like `approve(ctx)`, `ToolContext` unchanged) starts a run of the calling run's **own** agent, fire and forget, resolving `HandoffResult { runId, deduplicated }`. The opt-in is `handoff.on({ schema?, maxPerRun?, idempotencyKey?(p), concurrencyKey?(p) })` (channel `agent` = `AGENT_CHANNEL_NAME`, id `HANDOFF_SUBSCRIPTION_ID` `handoff`, at most one per agent; `maxPerRun` default `DEFAULT_MAX_HANDOFFS_PER_RUN` 100, a positive safe integer else `InvalidAgentDefinitionError`, from `handoff.on()`, from the engine's registration check (`assertHandoffSubscription()` in `assertRegistrable`, so a hand-built subscription is refused too) and again per call (`maxPerRunOf()`, `handoff/helpers.ts`)), served by `agentChannel()` (`channel/agent.ts`: name only, no `start`/`in`/`out`; a bare `Engine` lists it, `@chamvi/app`'s engine module contributes it). The engine provides an internal `HandoffHost { getAgent, effects, dispatch(envelope, parent), serial(runId, fn), inflight }` under `HANDOFF_CONTEXT` (`handoff/constants.ts`, not exported; set in the constructor like `MODEL_CONTEXT`), reached through `inject`; its `dispatch` is the protected `createRun(envelope, parent?)`, the body of `dispatch()`, which strips a `parent` any caller passes (`DispatchEnvelope` has no such field), so `engine.dispatch()` and `ctx.dispatch()` never forge lineage. Order per call: a tool frame (else `InvalidRunStateError`, also for another run's context); the run's id, agent, invoker and parent come from the copy the engine binds to each execution's `RunContext` before any tool runs (`bindRunSnapshot()`/`runSnapshotOf()`, `handoff/helpers.ts`, a module-private `WeakMap`), never from `ctx.run`, so tool code writing to `ctx.run` cannot pick another agent, widen the invoker or drop the parent, the host (`ContextNotProvidedError`), the input (`isObject`, `payload` required, keys non-empty strings without NUL, the concurrency key and address at most 255; `ValidationError`), the subscription (`Agent "<a>" accepts no hand-offs: add handoff.on() to its channels.`), depth (`MAX_HANDOFF_DEPTH` 1: a run whose `trigger.parent.kind` is `handoff` gets `A handed-off run cannot hand off again (depth 1).`), the schema (validup issues, the parsed value is the payload), the keys: concurrency key the input's else `subscription.concurrencyKey(payload)`; the claimed idempotency key `handoff:<key>` (`sha256:<hex>` of it above 255 characters, `claimKey()`), `<key>` the input's, else `subscription.idempotencyKey(payload)`, else `<parentRunId>:<stableHash({ payload, concurrencyKey, address })>` (a given key is not run-scoped, so a second run dedupes; scope `<agent>:agent` plus the invoker). The effect key is `<runId>:handoff:<stableHash({ payload, key, concurrencyKey, address })>`, value `{ runId, deduplicated }`: an in-flight identical call shares its promise (`inflight`, looked up and set without an await in between), a recorded call returns the record. Then under `serial(runId)` the record is read again (an earlier call may have written it meanwhile), then the durable count (effect `handoff-count:<runId>` = `{ count, calls }`, `calls` the effect key hashes the slots were spent on, `readCount()`): a call already in `calls` (its record lost) skips the limit and redoes the deduplicating dispatch; else it is checked against `maxPerRun` (`Run <id> reached its <n> hand-offs (handoff.on({ maxPerRun })).`) and written `count + 1` with the call before the dispatch, so a crash spends the call's slot once and a deduplicated hand-off counts too, the dispatch `{ agent, trigger: 'handoff', channel: 'agent', payload, idempotencyKey, concurrencyKey?, address?, invoker? }` with the parent's invoker snapshot (never widened; none for a cron parent) and `parent = { kind: 'handoff', runId, agent, depth: 1 }`, then the record (a failing write is logged with `console.error`, the call still resolves; dispatch dedupes the redo). The child's outbound names its channel (`agent` has no `out`, so `findOne()` without a name is `undefined`); `address` becomes `trigger.address`/`Run.address`. Under `runJob()` the drain interrupts children the job's engine picked up; recovery requeues them. Delegation (028c, waits for the child) reuses `agentChannel()` with its own subscription id.

```ts
type TriggerEnvelope = {
    id: string;              // defaults to a UUID
    agent: string;
    trigger: string;         // the subscription id, e.g. 'http'
    channel: string;         // the channel the run came from, e.g. 'mcp'
    payload: unknown;
    idempotencyKey?: string;
    concurrencyKey?: string;
    address?: string;        // where the run came from on that channel (an issue, a thread, a caller); also Run.address
    attachments?: Artifact[];
    invoker?: Invoker;       // { id, kind, name?, permissions }, from an authenticator only
    parent?: TriggerParent;  // { kind: 'handoff', runId, agent, depth }: set only by startHandoff(), dropped from any dispatch
    receivedAt: Date;        // defaults to now
};
```

Envelopes stored before plan 026 have `source` and `thread`; `normalizeEnvelope()` (`trigger/helpers.ts`, public, used by both store mappers) fills `channel` from `source` and `address` from `thread` when absent and drops both legacy keys (`Run.address` reads the existing `thread` column; no migration).

`dispatch` validates a given invoker (non-empty `id` and `kind`, `permissions` an array of strings, `ValidationError` before any write) and stores a copy of only those fields. It is a snapshot (identity and grants, never a token): a run paused on an approval keeps it, and revoking a grant does not reach a run that holds it. The idempotency scope includes the invoker (see Intake), so a deduplicated dispatch always comes from the invoker of the run it returns. Tool code reads it as `context.run.trigger.invoker` (tools and the factory's `run`) and `ctx.run.trigger.invoker` (effect hooks, agent hooks).

The envelope (channel, trigger, payload) is rendered as a JSON block and becomes the run's first user message: string content, or with attachments `[{ type: 'text', text }, ...one file part per attachment]` whose `data` is the marker `chamvi-artifact:<id>` (`ARTIFACT_URI_PREFIX`, internal). `TriggerEnvelope.attachments?: Artifact[]` holds their metadata; `DispatchEnvelope.attachments?: ArtifactInput[]` takes the bytes.

## Execution ceilings and channel HTTP policies (plan 033)

`AgentDefinition.concurrencyMaxRuns?: number | false` and `ChannelSubscription.concurrencyMaxRuns?: number | false` are nested shared-store execution ceilings; all subscription builders (`http`, `webhook`, `github`, `cron`, `handoff` and named channel instances) forward the setting. `assertConcurrencyMaxRuns()` (`channel/concurrency.ts`, public) accepts undefined/false or a positive safe integer, else `InvalidAgentDefinitionError`; `defineAgent()` and engine registration validate both levels, including hand-built definitions. `false` removes only that level's numerical ceiling. `EngineOptions.concurrencyMaxRuns`/`CHAMVI_MAX_CONCURRENT_RUNS` stays engine-local. Renaming the pre-existing TypeScript engine option to `concurrencyMaxRuns` is breaking; the environment variable is unchanged.

`engine/queue/admission.ts` reads live definitions through `RunQueueOptions.getAgent` (like `Engine.getAgent`, a synchronous registered-agent lookup returning undefined when absent, without loading, creation or I/O); an agent with any numerical cap uses `admission:<agent>` with a fresh UUID owner and `claimTtlMs` lease around count, claim and queued-to-running transition (status and owner guarded), including starts of uncapped siblings. Agent counts include every running run; subscription counts match `run.trigger.trigger`, not `channel` (HTTP and MCP share `http`). A direct dispatch without a matching subscription takes only the agent ceiling. Uncapped agents skip the admission count path. Cancellation bypasses numerical blocking. The existing concurrency-key lock nests inside admission; release/reporting failures cannot discard a transitioned run before launch, even with a throwing `onError`. Guarantees require compatible replica definitions and critical-section store operations finishing inside the lock TTL. Waiting/interrupted runs consume no numerical capacity but keep their concurrency keys. Queued runs are scanned FIFO with blocked work bypassed, not weighted fairness; backlog is durable and storage-unbounded. No caps are stored in envelopes and no migration or broker is added.

`HttpAppOptions.channelRateLimits?: Record<string, false | ChannelRateLimitOptions>` (`app/types.ts`, public; policy `{ max, windowMs? }`) is forwarded unchanged by `httpModule()`. `plugins/channels.ts` validates exact mounted input-channel names, a positive safe `max` and a positive timer-safe `windowMs` (default 60 s); `InvalidAgentDefinitionError` before serving. Omitted entries retain the general shared per-client bucket; explicit policies replace it with a separate per-channel/client bucket, also with `rateLimit: false`; `false` skips only that mounted POST endpoint and subpaths, never unknown paths or other methods. Buckets are HTTP-app-local, not distributed run-store state. Matching respects normalized basePath, case and path boundaries. JSON 429, CORS, Retry-After and rate headers remain; IP lookup uses the app's trusted-proxy configuration, not the limiter library's permissive default. Signatures/auth/body caps are unchanged. No new env variable. A 202 acknowledges stored acceptance, not execution. GitHub does not automatically redeliver failed deliveries. Operators configure known ingress sources in app `trustProxy`; chart ingress settings do not do so automatically.

## Run Lifecycle

Run statuses are exactly `queued | running | waiting | completed | failed | cancelled | interrupted`. Steps are `llm | tool | wait`.

```
dispatch -> queued -> running -> completed | failed | cancelled
running -> waiting (a tool awaits approve()) -> queued (an answer or the timeout) -> running
running -> interrupted (drain) -> queued (recover) -> running
running with an expired claim (crash) -> queued (recover) -> running
```

- **Intake**: `dispatch` first refuses an `idempotencyKey`, `concurrencyKey` or `address` above `TRIGGER_KEY_MAX_LENGTH` (255, the store's varchar width) or with a NUL (`assertTriggerKey()`, `trigger/key.ts`, `ValidationError`, before any store write); channels (`webhookChannel()`, `githubChannel()`) use the same helper. With an `idempotencyKey`, `dispatch` claims `(scope, key)` in the `IIdempotencyStore` (TTL 7 days); the scope is `<agent>:<channel>`, and with an invoker `<agent>:<channel>:<kind>:<id>` with `kind` and `id` each `encodeURIComponent`-ed (`idempotencyScope()`, `trigger/helpers.ts`), so two invokers sending the same key get a run each and one principal cannot squat another's key; a duplicate returns the existing run id with `deduplicated: true`. A key whose run was never created (createRun failed after the claim) is healed by the next dispatch, which creates the run under the reserved id; `createRun` is insert-if-absent, so concurrent healers create it once.
- **Attachments**: `dispatch` validates each `ArtifactInput` (`mediaType` `type/subtype` without parameters, optional string `filename`, `data` a `Uint8Array`; `ValidationError`) before any store write, then, after the idempotency dedupe returned (a duplicate stores nothing), stores each as an artifact of the run (id `<runId>.<index>` from `attachmentIds()` in `artifact/module.ts`, the index zero-padded to one width per dispatch, at least 4 digits, so `listArtifacts` (createdAt, then id) returns the input order; `size` = byte length, `createdAt` = run createdAt) and creates the run. Tool artifacts (`artifacts.put()`) keep `randomUUID()` ids. `storeArtifact` relies on `putArtifact`'s insert-if-absent: when the id is taken by the same run it returns the stored artifact (another run's: `InvalidRunStateError`), so concurrent healers of one reserved key write to the same ids, the second write is a no-op and `trigger.attachments` always names what the store holds (the first writer's bytes). A crash between storing and `createRun` leaves orphan artifacts (accepted; nothing purges artifacts yet), and a racing healer that sends more attachments than the winner leaves its extra indexes listed on the run.
- **Scheduling** (`engine/queue.ts`): a pass lists `queued` runs FIFO (createdAt, then id) and starts them up to `concurrencyMaxRuns`. **Execution guard**: a pass that found queued runs first builds a start predicate (`prepareStart`, one `listAgentRevisions()` read, skipped while no folder agent is registered): a run may start when `cancelRequested` (it settles `cancelled`), or when its agent is registered here and is a code agent or loaded at the stored marker's hash; any other run is skipped before any claim and stays `queued` for a replica that has the agent's current revision (never failed with `unknown agent`). `execute()` re-checks after the claim (`isCurrent`, one `getAgentRevision`) and hands a run whose agent was removed or replaced meanwhile back to `queued` (owner-guarded); recovery requeues as before, so the guard also covers recovered runs; `tick()` keeps skipping approval deliveries of unknown agents. A keyed run starts only when no other run of the same agent and `concurrencyKey` is `running`, `waiting` or `interrupted`; check, claim and transition happen under a store lock `concurrency:<agent>:<key>` so it holds across replicas.
- **Claims**: `claimRun(id, owner, claimTtlMs)` is a lease, renewed every `claimTtlMs / 3`. The poll runs on the same interval and calls `tick()` (approval expiry) and `recover()`. Every write of a running run is conditional on status and owner; an engine that loses its lease aborts the execution, writes nothing more and reports a `LeaseLostError` to `onError`.
- **Execution** (`engine/execute.ts`): one `ToolLoopAgent.stream()` call per execution (consumed to the end; settling reads the result's `steps`, `finishReason`, `text`, `output` promises), starting from the latest checkpoint. Checkpoints hold the stored messages (artifact markers); the model gets a hydrated copy whose marked file parts carry the bytes from `readArtifact` (a missing one fails the run with `ArtifactNotFoundError`), also the file items of a tool result's `content` output a tool built with `artifactFilePart(artifact)` (public, `artifact/module.ts`: `{ type: 'file', mediaType, filename?, data: { type: 'data', data: <marker> } }`), hydrated again per model call through the `ToolLoopAgent`'s `prepareStep` (a result made in this execution reaches the next model call with its bytes, while the response messages the checkpoint saves keep the marker), and the engine saves `[...storedInitial, ...responseMessages]`, so the pending-call path after an approval works on stored messages. Each `text-delta`/`reasoning-delta` part is emitted as `run.delta` (`RunDelta { runId, step, kind: 'text' | 'reasoning', text }`, `step` = the checkpoint `stepIndex` the step is saved under); deltas are never stored, local to the executing replica and never emitted once the execution was abandoned. No opt-out: every AI SDK provider streams. A model call that fails mid-stream (an `error` part) still ends its step: the AI SDK finishes it with finish reason `error`, so the engine appends the `llm` step (the partial text) and saves its checkpoint before the run fails with that error (unlike the former `generate()`, which wrote nothing; pinned in `stream.spec.ts`). A step whose provider stream closed without its finish part (the AI SDK then synthesizes finish reason `other` and never executes the step's tool calls) fails the run with `IncompleteResponseError` (`incomplete_response`); the engine tells it apart through `onLanguageModelCallEnd`, which fires only for a received finish, so a provider that reports `other` itself still completes.
- **Structured output**: with `output`, a `completed` run's `output` is the parsed value (else the text); a final answer that fails to parse or validate (`NoOutputGeneratedError` or a schema failure) fails the run with `ValidationError` (`validation_error`, message from the cause, the cause cut to `MAX_ERROR_CAUSE_LENGTH` 500 characters plus an ellipsis, `execute/constants.ts`). Before parsing, a loop end with no answer fails with `IncompleteResponseError` (`incomplete_response`, `incompleteOutput()` in `execute/helpers.ts`): finish reason `length` (cut answer) or `tool-calls` outside a budget stop (a call nothing executed, e.g. a tool without `execute`, named in the message). A plain agent keeps completing with the text in both cases (decided: its text is still usable and the llm step records the finish reason). The "step limit reached by an earlier execution" branch parses the checkpoint's last assistant text through `output.parseCompleteOutput` with the same rules (a `length` checkpoint is incomplete). The `ToolLoopAgent` gets `withoutPartialOutput(output)` (`execute/helpers.ts`): a prototype copy whose `parsePartialOutput` returns `{ partial: text }` without parsing, so the AI SDK neither re-parses the accumulated answer per delta nor holds deltas back (returning `undefined` would publish the whole text at `text-end` only); `parseCompleteOutput` and `responseFormat` stay the agent's. After every step the engine appends the steps and saves a checkpoint (messages plus the step's `finishReason`). A cancel or drain abort lets the step-end writes in flight finish (all tool rows and the checkpoint of a completed step), so a recovery does not redo a step whose tools already ran; an abandon guard then stops a still-running generate from writing after the run settled. Each execution owns an `AbortController` combined into the signal the agent and the tools get (`run.signal`); it aborts on every exit, so a throw while consuming the stream (e.g. a throwing `onError` behind a failing `run.delta` listener) cancels the model stream instead of leaving it open.
- **Budgets** (`engine/budget.ts`): `maxSteps` and `maxTokens` are stop conditions, `timeoutMs` an abort signal per execution (built on the `IClock`). Stopped by a budget while the last step asked for tool calls: `failed` with `BudgetExceeded`; otherwise `completed` (a plain agent), or for an agent with `output` the structured-output rules apply (a `length` finish fails with `incomplete_response`). Timeout: `failed` with `Timeout`.
- **Tool errors** go back to the model as tool-error results; only `FatalToolError` (and infrastructure or store failures) fail the run.
- **Cancel**: aborts a local execution (`cancelled`), or marks a `queued`/`waiting` run cancelled. A run `running` on another replica (or `interrupted`) gets `cancelRequested: true`; the owner sees it in `recover()` on its next poll and aborts with stop `cancel`, and an execution that starts on such a run settles it `cancelled` without a model call. A cancel that races a pause (the abort cannot interrupt the `waiting` write) cancels the run the pause left waiting, without delivering the approval.
- **Drain**: `drain({ timeoutMs })` stops every channel first, then stops polling and starting runs, waits for in-flight runs (default 30 s), then aborts the rest and marks them `interrupted` with the claim released. `stop()` stops the channels, then only polling.
- **Recovery**: `recover()` (on `start()` and every poll) claims each `running` or `interrupted` run whose claim expired or was released and requeues it; the next execution continues from the latest checkpoint. A step whose checkpoint never landed runs again.

## Approvals and Hooks

Durable `approve()` (plan 026) replaced the `approvals` map, the AI SDK `toolApproval` path and `approvalTimeoutMs`:

- **Tool-call frame** (`effect/frame.ts`, internal): `wrapToolsForRun(tools, ctx, store, { allow?, hooks?, onSuspend?, stepIndex? })` runs every call inside an `AsyncLocalStorage` frame `{ runId, toolCallId, toolName, stepIndex, approvals, ... }` (`stepIndex` read per call: the checkpoint index of the model step that made the call; the pending calls' checkpoint index while they replay) (`runToolCall`, `currentToolCall`). Order per call: frame, `allow` (`ToolNotAllowedError`), `beforeToolExecution` (its result is the input; a changed one is re-validated through the tool's `inputSchema`, a failure a `ValidationError` tool error), effect lookup and execute (the effect key from the final input), `afterToolExecution` (on a fresh and on a recorded result; a streaming tool's final value; never for a tool error). A thrown `ToolDeniedError` (`tool_denied`) is a tool error, `FatalToolError` still fails the run. Tools without `execute` pass through untouched.
- **`approve(ctx, { title, body?, options?, multiple?, timeoutMs? })`** (`approval/request.ts`; `ChannelHandle.approve()` is the same with `channel` and `address`): outside a frame, or in a streaming tool's body, `InvalidRunStateError`; `timeoutMs` default `DEFAULT_APPROVAL_TIMEOUT_MS` 24 h, 1 to `APPROVAL_TIMEOUT_MAX_MS` (2^31 - 1), else `ValidationError`. The n-th call of a frame (0-based, taken before any await) has `approvalId = <stepIndex>:<toolCallId>:<n>` (the step index, so a provider that reuses a call id in a later step asks again instead of reading an earlier step's decision); a decision recorded under the effect key `approval:<runId>:<approvalId>` (`approvalDecisionKey`) is returned, else the request is stashed on the frame (the first suspension of the call wins) and an internal `SuspendSignal` thrown. It sends nothing.
- **Suspend**: the wrapper catches the signal, records the request in call order and answers the AI SDK with `SUSPENDED_RESULT` (never stored); a stop condition ends the loop after that step. The checkpoint keeps the assistant message's tool calls and drops the suspended calls' results (`withoutResults`), no `tool` step for them; then `pause()` moves `running -> waiting` with `WaitPoint { kind: 'approval', approvalId, toolName, toolCallId, title, body?, channel?, address?, expiresAt, notifiedAt? }` from the first suspended request in call order (one approval per pause; the others stay pending and suspend again after the resume; parallel identical effect calls share one application, so a call whose shared application suspended stays pending on the same approval and gets the recorded result on replay), releasing claim and slot (a keyed run keeps its key blocked). Re-pausing on the same approval keeps the wait point, so the approval the owner was asked stays answerable; the `approvalId` is the wait point's identity (`answer()` and the delivery compare it).
- **Delivery** (`deliverApproval`): once the wait point is stored and it names a channel, the engine sends, detached from the execution (tracked in `deliveries`, awaited by `idle()` and `drain()`, so a slow `out` holds neither the slot nor the executions entry and a resume meanwhile starts the next execution cleanly; an execution only removes its own executions entry, and the queue never starts a run whose previous execution still holds its slot), `ChannelMessage { kind: 'approval', key: '<runId>:<approvalId>', title, body, approvalId, expiresAt }` (never the token) through that channel's `out` to `waiting.address`, with `{ signal, trigger }`, under the store lock `notify:<runId>:<approvalId>` held for one attempt (aborted after `claimTtlMs`), and records `waiting.notifiedAt`. `tick()` re-sends on every poll while it is missing; a crash before the wait-point write sends nothing, after it re-sends under the same key; a channel the engine no longer has goes to `onError` per attempt. `approve()` without a channel sends nothing (inbox and API only).
- **Answer** (`answer()`): `approve(runId, { approvalId, approved, reason?, approver? })` (`ApprovalAnswer`) and the `tick()` timeout (`approval timed out`, denied) move `waiting -> queued` (guarded by `expectStatus`, so only one answer writes), record the decision with `putEffect('approval:<runId>:<approvalId>', { approved, reason?, approver? })`, append a `wait` step (`name` the tool, input `{ toolCallId, title, body? }`, output `{ approvalId, approved, reason, approver? }`), then clear `waiting`. A failure undoes back to `waiting`, so the wait point stays answerable. `approve()` validates the approver before any store read and refuses a run that is not waiting, another `approvalId` or a wait point at or past `expiresAt` with `InvalidRunStateError`; a run that moved on meanwhile is `InvalidRunStateError` (the `stale` factory, also for the `tick()` timeout, which ignores it).
- **Options** (plan 031b, `approval/helpers.ts`): `options: ApprovalOption[]` (`{ id, label, detail? }`) and `multiple` are checked by `toApprovalOptions()` in `requestApproval` (`ValidationError` tool error: 1 to `APPROVAL_OPTIONS_MAX` 20 options, ids `APPROVAL_OPTION_ID_PATTERN` (128 characters, no whitespace) and unique, a label one non-blank line (no C0/C1 control, U+2028 or U+2029, since channels write labels raw) of at most `APPROVAL_OPTION_LABEL_MAX_LENGTH` 200, a detail at most `APPROVAL_OPTION_DETAIL_MAX_LENGTH` 20 000 and `APPROVAL_OPTIONS_DETAIL_MAX_LENGTH` 100 000 together, `multiple` a boolean, `true` needing options (`false` without options is plain); other keys dropped) and copied onto `ApprovalRequest` and the `WaitPoint` (jsonb, no migration; `multiple` only when true, a plain request gets neither key). `engine.approve()` checks `ApprovalAnswer.selected` with `assertSelectionShape()` (at most 20 distinct strings) before the store read and with `toSelection()` after the state checks (`ValidationError`, the run keeps waiting): a plain wait point takes none, a denial none (an empty one dropped), a single choice exactly one, a multiple choice at least one, all known ids; the decision effect and the `wait` step's `output` get `selected` in option order, the step's `input` the `options` (details included) and `multiple: true`; the `tick()` timeout never selects. `toApprovalDecision` reads `selected` back only as a string array, so a recorded plain decision stays plain; replay goes through `fitRecordedDecision()`: a recorded denial as is, an approval with `selected` re-ordered to the options the tool passes now, or `{ approved: false, reason: 'options changed' }` (approver kept) when it no longer fits them under `toSelection()`'s rules (an id not offered, a single choice now, a selection for a now plain request, none for a request that gained options), so a tool never gets an id it did not offer. `deliverApproval` spreads `options`/`multiple` into the `ChannelMessage`; `consoleChannel()` prints `select one:` (or `select one or more:`) and `option <id>: <label>` lines before the `approval ... waits` line.
- **Pending calls** (`engine/execute/`): the next execution first finds the checkpoint's assistant tool calls without a result (`pendingToolCalls`) and runs them in order through the wrapped tool set with their recorded ids (`executePendingCall`), re-applying what the AI SDK would: `toolPolicy` (`ToolNotAllowedError`), the input schema parse (`ValidationError` result), the `contextSchema` check for third-party tools (fails the run), the hooks. After each finished call the checkpoint gets its result first (`withToolResults`, saved under the same `stepIndex`), then its `tool` step, so a drain, crash or lost lease after it never runs it again; no further call starts once the execution was aborted, and an abort waits for that write before settling. A call that suspends again pauses without a model call. Then the model loop starts. The model sees only the tool's result; the decision lives on the `wait` step. Code before `approve()` runs again on resume (documented replay rule, as for crash recovery). A checkpoint with pending calls gets one step beyond `maxSteps`.
- No resume tokens: an approval is answered only by run and approval id (`engine.approve()`, `@chamvi/http`'s authenticated `POST /runs/:id/approve` and MCP `approve_run`), so there is no `resumeSecret` and no message carries a credential.

## Store Contract

The store is a set of small interfaces combined as `IStore` (`src/store/types.ts`):

| Interface | Holds |
|-----------|-------|
| `IRunStore` | Runs; `updateRun` with `expectStatus`/`expectOwner` guards; `listRuns` ordered by createdAt then id (both ascending, or both descending with `order: 'desc'`), unbounded without `limit`; `claimRun`/`renewClaim` leases |
| `IStepStore` | Append-only steps per run |
| `ICheckpointStore` | Latest checkpoint per run (highest `stepIndex`; equal index replaces) |
| `IIdempotencyStore` | `claimKey(scope, key, runId, ttl)`: first caller wins |
| `ILockStore` | `acquire`/`release` of keyed leases |
| `IEffectStore` | Recorded effect results by effect key |
| `IStateStore` | Per-agent KV (`kvSet(..., undefined)` removes the key; `kvList(agent, { limit?, offset? })` in key code-point order, unbounded without `limit`) and document collections (`where` = top-level equality) |
| `IAgentRevisionStore` | One revision marker per folder agent, `AgentRevision { agent, hash, changedAt }` (no code): `getAgentRevision`, `setAgentRevision` (upsert), `deleteAgentRevision` (missing is a no-op), `listAgentRevisions` (agent code-point order); copied in and out |
| `IArtifactStore` | `putArtifact(artifact, data)` (atomic insert-if-absent, `false` keeps the stored one), `getArtifact` (metadata), `readArtifact` (bytes, a plain `Uint8Array`), `listArtifacts(runId)` (createdAt, then id); bytes copied in and out |

Rules every implementation must keep: a TTL created at T with `ttlMs` is expired at exactly `T + ttlMs`; values are copied in and out (no aliasing); atomic operations are atomic across callers. `MemoryStore` implements it in-process (structured clones, no await between check and write). `describeStoreContract((clock) => store)` from `@chamvi/test-kit` is the shared Vitest suite every store must pass; the factory must use the given `ControllableClock` for expiry. Redis is never required.

`TypeormStore` (`@chamvi/store-typeorm`) is the TypeORM store (PostgreSQL only). Every method goes through the entities' repositories and query builders; the only hand-written SQL is the `jsonb_exists` key check in `docList` (TypeORM has no key-existence operator), containment uses `JsonContains`; `store/helpers.ts` maps entities to `Run`, `Step` and `Checkpoint` (a `RETURNING` row is hydrated through the entity metadata). Every atomic operation is one statement: `insert().orIgnore()` returning `id` (`createRun`, `putArtifact`), `insert().orUpdate()` with the overwrite condition `expires_at <= now` returning a row (`claimKey`, `acquire`), a conditional `update()` (`claimRun`, `renewClaim`, the `updateRun` guards, the latter returning `*`) and `insert().orUpdate()` with the overwrite condition `step_index <=` (`saveCheckpoint`). Time comes from the `IClock` as a parameter, never the database's `now()`. Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt` and `waiting.notifiedAt` are revived as `Date`. Only the latest checkpoint is kept. Artifacts live in `chamvi_artifacts` (`ArtifactEntity`: `id` varchar(128) PK, `run_id` indexed, `agent`, `media_type`, `filename` nullable, `size` int, `data` `bytea` with `select: false`, `created_at` timestamptz; migration `1792368000000-artifacts.ts`); `chamvi_idempotency_keys.scope` is varchar(1024) (migration `1792454400000-idempotency-scope.ts`, a hand-written `ALTER COLUMN ... TYPE`, since TypeORM's generated length change drops and re-adds the column); `chamvi_kv.key` is `COLLATE "C"` (migration `1792540800000-kv-key-collation.ts`, `KvKeyCollation1792540800000`, hand-written the same way), so `kvList` orders by code point; markers live in `chamvi_agent_revisions` (`AgentRevisionEntity`: `agent` varchar(64) `COLLATE "C"` PK, `hash` varchar(128), `changed_at` timestamptz; migration `1792627200000-agent-revisions.ts`, `AgentRevisions1792627200000`), `setAgentRevision` a repository `upsert` on `agent` (no compare needed: the engine holds `agents:<name>`), `listAgentRevisions` ordered by `agent`; `getArtifact`/`listArtifacts` never load `data`, `readArtifact` returns a plain `Uint8Array`. `migrateStore(dataSource)` runs the migrations under the advisory lock `chamvi:migrations`; `pendingMigrations(dataSource)` names the migrations not run yet through `MigrationExecutor.getPendingMigrations()` (read-only: it never creates the migrations table); `purgeExpired(now?)` deletes expired idempotency keys and locks (nothing calls it automatically yet). Documented divergences from `MemoryStore`: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, `putEffect(key, undefined)` reads `{ result: null }`, `docUpsert(..., undefined)` reads `doc: null`, `docList` `where` is `jsonb` containment and orders by `id`, `listRuns` ties use `COLLATE "C"`.

## Idempotency and Side Effects

1. Trigger dedupe at intake via `IIdempotencyStore`.
2. Completed steps are never repeated: execution resumes from the latest checkpoint.
3. Side-effecting tools use `defineEffectTool()`. Per call the wrapper (`wrapToolsForRun`) returns the recorded result for the effect key, else asks `alreadyApplied(effectKey, input, ctx)`, else executes and records the result; both hooks get the `ToolContext` (`ctx.run`, `ctx.state`, `ctx.artifacts`), and a custom `effectKey(input, ctx, options)` also gets the AI SDK call options (`toolCallId`, `messages`, e.g. to key by model step). The default key is `${ctx.run.runId}:${toolName}:${sha256(canonical JSON of input)}`. A throwing execute records nothing; a crash between the effect and the record repeats it unless `alreadyApplied` finds it (`effectMarker(key)` is the hidden marker to embed). Parallel identical calls in one step share one application.

## Agent State

`createAgentState(agent, schema, store)`: KV (`state.get/set`) plus typed collections declared as `state: Record<name, StandardSchemaV1>` in `defineAgent`. `upsert` validates with the collection's Standard Schema, mapped through `@validup/standard-schema` (`ValidationError` with the validup `issues` on failure, nothing stored). With a schema, the model also gets `state_<coll>_list`, `state_<coll>_upsert` and `state_<coll>_remove` tools (`createStateTools(schema)`; chamvi tools reading `context.state`, upsert and remove are effect tools); user tools win on a name clash.

## Cron Channel

`@chamvi/channel-cron` (the former `@chamvi/scheduler`) is the cron channel; it depends on `hubwire` (croner inside) and `cron-parser` and is a peer of core.

- `cron.on(expression, { timezone?, overlap?, payload?, id? })` (`subscription/`) makes a subscription of the channel named `cron` (id default `cron:<expression>`); it validates the expression with cron-parser, the timezone with `Intl`, the overlap policy (default `skip`; `queue-one`, `allow`) and a non-empty `id` (`InvalidAgentDefinitionError`). `cronChannel({ name?, owner?, lockTtlMs?, onError? })` (`channel/`) is the channel; its `on()` makes subscriptions only it fires (a second instance, e.g. `cron-eu`), and `cron.on()` ones reach only the channel named `cron`.
- `start(ctx)` runs the internal `createScheduler({ engine, channel, owner?, lockTtlMs?, onError? })`, which builds one hubwire `defineScheduledComponent` per cron subscription of this channel in `engine.listAgents()`, named `cron:<agent>:<subscriptionId>`, with `lock: createStoreScheduleLock(engine.store, owner)` (`ILockStore.acquire`, never released) and `lockTtlMs` default `SCHEDULE_LOCK_TTL_MS` (10 min). hubwire's tick key is `${name}:${scheduledAt ISO}`. A code agent's subscription hubwire refuses (expression croner rejects, timezone) throws `InvalidAgentDefinitionError` out of `engine.start()`; a folder agent's (registered at a revision) goes to `onError` and leaves it unscheduled. `assertSchedulable(agent, channel?)` is the same check without scheduling (the app's `AGENT_CHECKS`).
- Live components: the channel keeps its components per agent (`buildAgentComponents()`, `scheduler/helpers.ts`) and follows `agents.changed`: `added` builds and starts the agent's components, `replaced` stops the old ones and builds the new, `removed` stops them. A replacement hubwire refuses goes to `onError` and leaves the agent unscheduled (never a throw). Retired components stop in the background; `stop()` (called first by `engine.drain()`/`stop()`) unsubscribes, stops every component and awaits their `settled()` plus the retired ones.
- `runOnStart: false` always: a start pass never takes hubwire's lock and would fire on every replica. hubwire skips a locked tick fired `lockTtlMs` or more late; `onSkip` is not wired (N - 1 replicas skip every tick). Lock, overlap and dispatch failures reach `onError(error, { agent, subscription })`.
- `fireCronSubscription({ engine, agent, subscription, scheduledAt })` is one tick: overlap check (over `engine.store`), then `dispatch` with `channel` the subscription's channel, payload `options.payload ?? { scheduledAt: ISO }`, idempotency key `<subscriptionId>@<scheduledAt ISO>` (the subscription's own `idempotencyKey()` is ignored), `concurrencyKey = subscription.concurrencyKey?.(payload) ?? (overlap === 'allow' ? undefined : subscription.id)`.
- Overlap: active runs are `queued | running | waiting | interrupted` of the agent filtered by `run.trigger.trigger`. `skip` skips while any is active, `queue-one` while one is `queued`, `allow` never. The check-then-dispatch race is made harmless by the default concurrency key (the extra run waits).
- `runJob({ engine, agent, subscription?, pollMs?, drainTimeoutMs?, signal? })` fires once at `engine.clock.now()` (the engine must hold the subscription's cron channel), then always starts the engine with `start({ channels: false })` (a job never starts cron schedules or sockets) and calls `engine.tick()` once (so a skipped tick still recovers leftovers of earlier jobs and times out expired approvals), waits via `run.updated` plus an `engine.getRun` poll (`pollMs`, default 1 s, covers another replica) for `completed | failed | cancelled | waiting`, or for `queued` behind a `waiting` run of the same concurrency key (`queue-one` behind an approval), then `drain({ timeoutMs })` (default 30 s). Exit code 1 for `failed`/`cancelled`, else 0; an overlap skip returns `skipped` after the drain. It starts a full engine over the shared store (every queued run of every agent), so size the drain timeout. `signal` (for the CLI's SIGTERM): already aborted when called, it fires nothing and starts nothing (`skipped`); aborted during the dispatch, the engine never starts and the stored run answers (`queued`, exit 0); checked again after `engine.start()`, so a stop that arrived meanwhile skips the approval tick; aborted while waiting, the wait ends and the drain runs, answering the run as the drain left it (`interrupted`, exit 0).

## HTTP

`@chamvi/http` is one routup v6 `App` per chamvi app, a peer of core like the channel packages.

- `createHttpApp({ engine, agents?, auth, basePath?, trustProxy?, shutdown?, bodyLimit?, stream?, mcp?, cors?, rateLimit?, metrics?, readyTimeoutMs?, onError?, routes?, channels? })`. The store (`listRuns`, `listSteps`, state), the agents (all, or the names in `agents`, resolved by `selectAgents()` in `app/helpers.ts` at construction: a name the engine lacks or given twice is `InvalidAgentDefinitionError`; the others, also agents registered later, have no routes or MCP tools in this app, while a mounted channel serves every agent subscribing to it) and the clock come from the engine (`engine.store`, `engine.listAgents()`, `engine.clock`); `buildContext()` copies the store and clock into the internal `HttpContext` and reads the agents live (see Live agents). `basePath` loses its trailing slashes (`normalizeBasePath()`, `app/helpers.ts`; `/` is no prefix), so every reader sees one prefix. An empty `auth` array, a `basePath` that is then no static path (the extra routes' shape) and a `stream.maxOpen` that is no positive integer throw `InvalidAgentDefinitionError`. Order: plugins, health, agents (incl. `/schedules`), runs, channels, extra routes, MCP, a trailing catch-all 404, the error handler. Route modules share one internal `HttpContext` (`app/types.ts`). **Live agents**: `HttpContext.agents` is `HttpAgents { get, list, names }` (`createLiveAgents()`, `app/helpers.ts`), reading `engine.getAgent`/`listAgents()` on every call (filtered by `agents`), so routes, `GET /agents`, `/schedules`, `GET /runs` agent filters, extra routes (`HttpRouteContext.agents` is a getter) and MCP follow `putAgent`/`removeAgent` at once; a named agent removed from the engine answers 404. `agentIssues?: () => readonly AgentIssue[]` (the app's load issues) is read per `GET /agents`, filtered by `agents`.

- Errors: every route under `basePath` answers `{ status, code, message, issues? }`, built by the error handler (never `toJSON()`, which would send `cause`); `withIssues` runs every issue tree through `boundIssues()` (`request/helpers.ts`), dropping a `received` value over `RECEIVED_MAX_LENGTH` whatever produced it (validators, a subscription schema, a core `ValidationError`), so a 400 never echoes a large body. `@ebec/http` errors keep their status (code lower-cased), validup errors are 400 `validation_error`, core codes map `RUN_NOT_FOUND` and `ARTIFACT_NOT_FOUND` 404, `INVALID_RUN_STATE` 409, `VALIDATION` 400 (`INVALID_AGENT_DEFINITION` at request time comes from an authenticator or `oidc()` mapper that resolved an invalid principal: 500 and `onError`); anything else is 500 `Internal Server Error` and goes to `onError`. Every 401 gets `WWW-Authenticate: Bearer`. Error responses start from `event.response.headers`, so CORS, `RateLimit-*` and `Retry-After` survive.
- Auth: `Authenticator = (request) => Promise<Principal | undefined>` (`undefined` lets the chain continue, a throw is a 401 remembered while later authenticators run; a resolved principal without a non-empty `id` and `kind` and a `permissions` array of strings is `InvalidAgentDefinitionError`, 500 and `onError`, and ends the chain); the chain runs once per request (memoized on `event.store`). Built-ins: `staticTokens({ tokens: [{ value, id, permissions }] })` (sha256-indexed, `value` at least 16 characters and unique, a non-empty `id` that several tokens may share), `authup()` (`@authup/server-adapter-web` `verifyRequest`; grants only from tokens whose `scope` has `global`), `oidc()` (vouchly; `principal` mapper and a non-empty `audience` per issuer required, as vouchly skips `aud` without one; untrusted issuer or malformed token passes on, unreachable issuer 503, an unknown `kid` 401; a mapper result without a non-empty `id` and `kind` or with `permissions` that are no string array throws `InvalidAgentDefinitionError`, a 500 reported to `onError`). Permissions `agent:<name>:run`, `agent:<name>:approve`, `run:read`, `run:cancel`, `state:read`, `state:write`, `tool:<agent>:<tool>` (read by core's `requireToolPermission()`, never checked by a route), `*`; a `*` segment matches one segment, segment counts must match. Routes match with core's `hasPermission(principal.permissions, wanted)`; http exports only `agentPermission()`, no matcher of its own.
- Reading runs: `run:read` or `agent:<run.agent>:run` (`GET /runs/:id`, the stream, MCP `get_run`); `GET /runs` and `list_runs` without `run:read` must filter to one agent the principal can run (one store query keeps `total` exact). 404 comes before 403 (run ids are random UUIDs).
- Body after authorization: every protected `POST`/`PATCH` authorizes before `readJsonBody` (so an unauthenticated client cannot make the server buffer `bodyLimit`). `POST /runs/:id/approve` authenticates, loads the run (`loadApprovableRun`, 404, no read permission needed), requires `agent:<agent>:approve` (403), then reads the body. Bodies: JSON media types only (415 at the first non-empty chunk), `bodyLimit` (413; a `content-length` above it is refused unread, which Node discards; a body refused part-way is drained up to `bodyLimit` more bytes, else answered with `connection: close`, because an unread remainder stalls the next request on a keep-alive socket), objects only for REST bodies (validup `Container` with chamvi's own `isString`/`isBoolean`/`isDefined` validators; unknown keys dropped), subscription payloads through the subscription's Standard Schema (`validatePayload`). U+0000 is refused as 400 at the edge (`assertNoNul` on path and query before any route, `isString`, webhook-derived keys and addresses, MCP `pattern`s), since Postgres varchar columns refuse it and a lookup would otherwise be a 500.
- Invoker: `toInvoker(principal)` (`auth/helpers.ts`) snapshots `id`, `kind`, `permissions` and a `name` from the claims (`name`, then `preferred_username`; never `email`, which every reader of the run would see; static tokens have none), never the claims themselves. `POST /agents/:name/runs` and MCP `run_<agent>` dispatch with it as `invoker`; `POST /runs/:id/approve` and MCP `approve_run` pass it as `approver`. Webhook and GitHub deliveries dispatch without one; it never comes from a body.
- `serializeRun()` drops `claim` and the invoker's `permissions` (keeping `id`, `kind`, `name`) from every run that leaves the package (REST, SSE, MCP), `serializeStep()` drops the `permissions` of a `wait` step's `output.approver` (`GET /runs/:id`, SSE): a `run:read` holder must not learn another principal's grants. Wire types `RunView` and `InvokerView` (`runs/types.ts`).
- SSE: subscribe to `engine.on` before the snapshot, send `run.updated` then steps after `Last-Event-ID` (`id` = step index) or `?after=<step index>` (non-negative integer, given once, else 400; a valid `Last-Event-ID` wins, a malformed one reads as absent), then live events (`run.delta` of the run as `event: delta`, `data: { step, kind, text }`, **no `id:`** so `Last-Event-ID` stays a step index; live only, local replica only, never replayed); a store poll every `stream.pollMs` (2 s, on the `IClock`) covers runs executing on another replica and sends `ping` when idle; the stream ends after a settled run. A failing snapshot is an error response (500, 404 for a run gone meanwhile), never an empty 200 stream. Cleanup (unsubscribe, clear the timer, leave `ctx.closers`) runs once: on end, when `write()` returns false, or on `event.request.signal` abort (srvx aborts it on client close). `maxMessageSize` is never passed (an oversize write reads as a disconnect). Bearer auth only: browser `EventSource` cannot send `Authorization`, so browsers use a fetch-based SSE reader that sends `Authorization` and `Last-Event-ID` (or `?after=`).
- Stream cap: one counter per app (`ctx.openStreams`, cap `stream.maxOpen`, default 1000) over open SSE streams and MCP `run_<agent>` waits (`waitSeconds > 0`); `acquireStreamSlot(ctx)` (`app/helpers.ts`) returns an idempotent release or `undefined`. The stream takes its slot after the `?after` check and the shutdown 503, releases it in its one-time cleanup (end, failed write, request abort, failed snapshot or poll, shutdown); over the cap it renders `503 service_unavailable` with `Retry-After: 5` (`STREAM_RETRY_AFTER_SECONDS`) through `renderError`, not reported to `onError`. An MCP wait over the cap answers at once like `waitSeconds: 0` (the run is dispatched, never failed); a wait releases in `finally`.
- MCP: `createMcpHandler()` from `@modelcontextprotocol/server` 2.3 (stateless legacy fallback), `maxRequestBodySize: bodyLimit`; the route reads a `POST` body itself (`readBodyBytes`, same limit and drain) and hands the SDK a buffered `Request`; one `McpServer` per request whose tools depend on the principal, passed with `event.request.signal` in `authInfo.extra` (the SDK's own `ctx.http.req.signal` never aborts on disconnect). Tools: `run_<agent>` per agent with an `http.on()` subscription the principal may run, its definition (payload JSON Schema with `$ref`s re-rooted at `#/properties/payload`, compiled by `fromJsonSchema`) built once per agent object by `buildRunTool` through `createRunToolSource` (a `WeakMap`, so a replaced agent, a new object, is rebuilt; the agents held at construction eagerly, where a failure fails the app, a later one on the first request that sees it, where a failure goes to `onError` once and its tool is skipped), which throws `InvalidAgentDefinitionError` for an uncompilable schema or a name above 64 characters (channel `mcp`; `waitSeconds` clamped to `maxWaitSeconds` 60; `waitForRun` resolves on `completed | failed | cancelled | waiting` via `run.updated` or a 1 s store poll, or with the stored run on timeout or abort, signal = request signal plus `mcpReq.signal` plus the app's shutdown; ), `get_run`, `list_runs`, `approve_run` (`{ runId, approvalId, approved, reason? }`, `loadApprovableRun` then `engine.approve()`, like `POST /runs/:id/approve`). Tool failures are `isError` results; non-HTTP, non-core errors go to `onError`. Idempotency scopes differ per transport and principal (`<agent>:mcp:<kind>:<id>` vs `<agent>:http:<kind>:<id>`, see Intake).
- **Choice answers** (plan 031b): `ApproveBody.selected?` (`isStringArray({ max: APPROVAL_OPTIONS_MAX, item: { min: 1, max: 128 } })` in `request/validators.ts`, `APPROVAL_OPTION_ID_MAX_LENGTH` in `runs/constants.ts`) and MCP `approve_run`'s `selected` (`maxItems` 20, the same item rule) are passed to `engine.approve()` only when given, which checks them against the wait point (400 `validation_error`); `GET /runs/:id`, SSE and `get_run` carry `waiting.options`/`multiple` as stored, `RunToolResult.waiting` spreads them in when present.
- Extra routes (`routes: HttpRoute[]`, `routes/module.ts`): the extension point other packages plug into (`@chamvi/ui`'s dashboard) without routup in their types; run intake belongs in a channel on the mount, not here. `HttpRoute { method, path, rateLimit?: false, handler(request, ctx) }`; the handler gets `{ request, readBody() }` (`request` a body-less copy with URL, method, headers and signal, so the limited path is the only way to the body; `readBody` = content-length check plus `readBodyBytes` with the JSON media type rule: 413, 415, raw bytes, memoized per request) and `HttpRouteContext { engine, agents, clock, onError }`, and returns `{ status, body? }` (`null` sent for a missing body, since routup hangs on `undefined`). Not authenticated by the app's authenticators; thrown errors render like any route's. `buildContext` refuses (`InvalidAgentDefinitionError`) a path without a leading `/`, with `:`, `*` or `{`, a duplicate method and path, a first segment in `RESERVED_ROUTE_SEGMENTS` (`app/constants.ts`) and the metrics path when metrics are on, all compared lower-cased because routup matches paths case-insensitively (`plugins/helpers.ts` lower-cases the request path the same way for the limiter skips, the stream check and `routeLabel()`). `rateLimit: false` routes skip the limiter; `routeLabel()` labels each route by its path. A string `body` is sent as `text/plain`, a `Uint8Array` as is (a `Response` built from `event.response.headers` like the artifact route, `application/octet-stream` unless the result's `headers` name a `content-type`), everything else but `null` as JSON; `HttpRouteResult.headers` are set on `event.response.headers` first, so a `content-type` there wins. `HttpRoute.prefix: true` registers `path` and `${path}{/*rest}` (routup's optional-group syntax, as the channel mount) and hands `HttpRouteRequest.subpath` (`routeSubpath()`, `routes/helpers.ts`: the raw, percent-encoded rest of the URL pathname after `basePath` and `path`, case kept, `''` for the path itself and for a plain route); `validateRoutes` also refuses a route of the same method at or under a prefix route (lower-cased) and a prefix route at or above the metrics path; `isUnlimitedRoute` and `routeLabel` (which takes the routes, labelling a prefix route `<path>/*`) match a prefix route on `path` and below `path/`. `HttpRouteContext.basePath` is the app's `basePath` (`''` by default).
- Plugins, in order: `@routup/cors` only when `cors` is given; `@routup/rate-limit` 300 per 60 s keyed by `getRequestIP(event)` (honours the App's `trustProxy`; the library default would trust any `X-Forwarded-For`), skipping `OPTIONS`, `/healthz`, `/readyz` and the metrics path, rendering 429 through the error handler; `@routup/prometheus` at `/metrics` with a fresh `prom-client` `Registry` per app, skipping `GET /runs/:id/stream`, its `path` label the route template from `routeLabel()` (`plugins/helpers.ts`, unknown paths `/_unmatched`; keep it in step with new routes). The limiter runs first so a 429 is not timed. `/healthz`, `/readyz`, `/metrics`, the channel mount and the extra routes (which check their own credentials) are the only routes the app's authenticators do not guard.
- Shutdown: `createShutdown({ engine, server?, readinessDelayMs?, drainTimeoutMs?, closeTimeoutMs?, onError? })` (time from `engine.clock`); `shutdown()` is idempotent and runs: `shuttingDown` (readiness fails), wait `readinessDelayMs` (0), the `onShutdown` callbacks in the order added (`@chamvi/app` registers the `stopping` hooks first; the http app registers one that sets `ctx.closed`, ends SSE streams, aborts MCP `run_<agent>` waits (they answer with the stored run) and closes the MCP handler; new streams and MCP requests then answer 503 without `onError`), `server.close()` (not awaited yet), `engine.drain({ timeoutMs: 30 s })` (channels stopped first), then at most `closeTimeoutMs` (5 s) for the close before `server.close(true)`. With srvx pass `gracefulShutdown: false` to `serve()`.

## GitHub

`@chamvi/github` connects a GitHub App through the `github` channel (deliveries in, comments out; it absorbed `@chamvi/notify-github` in plan 026); it depends on `@octokit/core` with `plugin-paginate-rest`, `@ebec/http` and `smob`, peers on core and `ai`, and needs `@chamvi/http` only for its tests (nx stays acyclic).

- `createGithubApp({ appId, privateKey, webhookSecret, installationId?, slug?, baseUrl?, clock?, fetch? })` validates eagerly (`InvalidAgentDefinitionError`: empty `appId`, a key that is no RSA private key, empty secrets, an `installationId` that is no positive integer, a non-empty `baseUrl` that is no absolute https URL without query or hash (`normalizeBaseUrl`; empty is the default API), a `slug` that is not `^[a-z0-9]+(-[a-z0-9]+)*$`, since a miscased slug would silently disable the self guard); literal `\n` in the PEM become newlines. App JWT: RS256 via `node:crypto`, `iat = now - 60 s`, `exp = now + 540 s`, `iss = appId`. Installation tokens are cached per installation and replaced when `now >= expiresAt - 5 min` on the `IClock`; concurrent callers share one exchange, a failure is not cached. `octokit(id)` builds a `PaginatedOctokit` per call with the cached token; `botLogin()` is `<slug>[bot]` from `slug` or one `GET /app` (single-flight, a failure not cached; an answer without `slug` is a failure, never a `[bot]` login); logins are compared case-insensitively (`isSameLogin`). Tokens, the key and JWTs are never logged or stored; a failed exchange rejects with Octokit's `RequestError` (its authorization header redacted).
- `github.on(events, { id?, filter?, idempotencyKey?, concurrencyKey?, selfEvents? })` (`subscription/`): channel `github`, id `github:<events joined by ','>`, events `name` or `name.action` (`^[a-z0-9_]+(\.[a-z0-9_]+)?$`, digits for `projects_v2_item`), default concurrency key `<full_name>#<issue|pull_request number>`, else `<full_name>`, else none. The payload is a `GithubEvent { name, action?, delivery, installationId?, payload }`. `github.to({ repo, number })` builds the address `<owner>/<repo>#<number>`; the channel instance has both bound to its own name.
- `githubChannel({ app, name?, mention?, approvalUrl?, timeoutMs?, bodyLimit?, onError?, clock? })` (`channel/`, every option checked when called): **`in`** (`receiveDelivery()`, `webhook/module.ts`), served by `createHttpApp({ channels })` at `POST /channels/<name>`: a subpath below it 404; `X-Hub-Signature-256` missing 401; `X-GitHub-Event` not `^[a-z0-9_]+$` or `X-GitHub-Delivery` not 1..255 characters without NUL 400; `@chamvi/http`'s `readRequestBody` with `bodyLimit` (default 1 MiB, 413), a non-JSON media type 415 (a form-encoded hook); HMAC-SHA256 over the raw bytes under every secret (constant time, all checked) else 401; non-JSON or non-object 400. Then per agent its first matching subscription of this channel and keys `subscription.idempotencyKey?.(event) ?? delivery`, `subscription.concurrencyKey(event)` and the address `<full_name>#<number>` for an event with an issue or pull request (`eventAddress`), all computed before any dispatch; a throwing `filter` or key function fails that agent only (`onError`, the others continue, answer 500), and `dispatch` refuses a key or address over 255 characters or with NUL (`assertTriggerKey`) the same way. With a match and a `Bot` sender whose login equals `botLogin()`, nothing is dispatched. Dispatch is sequential in agent order through `ctx.dispatch` without invoker; a failing agent goes to `onError` and the rest are still dispatched, then the answer is 500; else `202 { delivery, runs: [{ agent, runId, deduplicated }] }` (`runs: []` for ping, unmatched and self-sent events). The signature covers the body only, neither `X-GitHub-Delivery` nor `X-GitHub-Event`: a captured signed body replayed under fresh delivery ids (or under another event name an agent listens on, so `GithubEvent.name` is untrusted too) starts new runs (bounded per key by `concurrencyKey`, not in number), so exposed deployments give the subscription an `idempotencyKey` from body fields only and a `filter` that checks the body matches the event name.
- **`out(message, address)`** (`createCommentSender()`, `channel/out.ts`): `address` parsed as `owner/repo#n` (`parseAddress`, `REPO_PATTERN`, a positive number; else `ValidationError`); the installation is the event's for a run this channel started on the address's repository, else `app.installationFor()` of that repository (inside the send's timeout and signal; a failure `github_request`), else the event's for a run this channel started, else `app.installationId`, else `InvalidAgentDefinitionError` before any comment request. Per send: `app.octokit(installationId)` with the signal bound through `hook.before('request')`, page `GET .../issues/{n}/comments` (`since` = `receivedAt - 1 h`, `RECONCILE_SKEW_MS`, 100 per page) and resolve when a `Bot` comment whose login `isSameLogin(botLogin())` holds `effectMarker(markerKey(message.key))` (`markerKey`: the key when `^[\w:.-]{1,255}$` without `--`, else `sha256:<hex>`); else `POST` the comment: mention line (`@<login>` per `mention`, `LOGIN_PATTERN`), `### <title>` (when given; `neutralizeTitle`: whitespace runs collapsed, a zero-width joiner after every `@` and `#` and in `GH-<n>`, since titles come from tool code, so no mention or reference in it fires), the body cut to `COMMENT_BODY_MAX_LENGTH` 60 000 inside a fence one backtick longer than its longest run (at least three; runs over 31 broken with zero-width spaces), so mentions and `#123` inside notify nobody; for an approval `Waiting for approval until <ISO>.` plus `Approve or deny: <approvalUrl({ runId, approvalId, agent })>` (ids only) or the hint "Answer it in the chamvi UI or through POST /runs/:id/approve." (never the token; the comment is public), the run line, the marker. A send is bounded by `timeoutMs` (30 s, `GITHUB_CHANNEL_TIMEOUT_MS`) on the `IClock` (an `AbortController` armed before the first `await`, its reason the timeout error), below the 60 s notify lock. Failures: `GitHub <status>: <message>`, `GitHub request failed: <message>`, `GitHub did not answer within <ms>ms.` (code `github_request`). The token exchange and `GET /app` are bounded by `APP_REQUEST_TIMEOUT_MS`, so a cold app on a stalled GitHub can outlive the lock; the marker keeps a concurrent replica's send at one comment.
- **Choice approvals** (plan 031b): `renderOptions()` (`channel/helpers.ts`, internal) puts `Options (choose one):` (or `choose one or more`) and a fenced `- <id>: <label>` list (no detail) after the body, cutting the body to `COMMENT_BODY_MAX_LENGTH` minus the list's length; the link line reads `Choose and approve or deny: <link>`, without a link `Choose in the chamvi UI or through POST /runs/:id/approve with selected.` A plain approval renders as before.
- Tools act as `installationOf(app, ctx, target)` (`tools/helpers.ts`, plan 031a), per repository the tool names: (1) the event's `installationId` for a run of the channel `github` or of any name a `githubChannel({ app })` of the same app took (`registerChannelName`/`isChannelOf`, a `WeakMap` per app in `app/helpers.ts`; a payload of another channel never picks the installation) when the event's `repository.full_name` is the target (case-insensitive, no request); (2) `IGithubApp.installationFor(target)` (App JWT `GET /repos/{owner}/{repo}/installation`, cached per lower-cased `owner/repo` for `INSTALLATION_CACHE_TTL_MS` 10 min on the `IClock`, single-flight, a 404 `undefined` and not cached, a failure a `github_request` error and not cached; `repositoryToken` shares the cache); (3) the event's installation for any repository, else the app's `installationId` (a public repository the App is not installed on stays readable); else a `github_request` ChamviError, a tool error (never `FatalToolError`). `github_search_issues` targets the single `repo:` qualifier of its query (`searchTarget()`), else (3). The lookup is shared, so a caller only stops waiting on its run's signal (`untilAborted()`). `IGithubApp.installations()` lists `GET /app/installations` (paginated, not cached). Every installation request carries the run's `signal` (an Octokit `hook.before('request')` in `withOctokit`), so cancel, drain and the run timeout abort a stalled GitHub call. ## Sandbox and Coding

`@chamvi/sandbox` holds the contracts and shared rules, three providers implement them, `@chamvi/coding` adds the coding tools. Nothing in these packages throws `FatalToolError`: model input the model can correct is a core `ValidationError`, a workspace or provider failure a core `SandboxError` (`sandbox_error`), both tool errors; option misconfiguration is `InvalidAgentDefinitionError`.

- **Contracts** (plan 027a): `ISandboxProvider { name, create(options), find(runId, { deployment?, signal? }), collectGarbage({ deployment?, isSettled? }) }`; `IWorkspace { id, info, disposed, exec(argv, { cwd?, timeoutMs?, stdin?, signal? }), readFile(path), readBytes(path), writeFile(path, content: string | Uint8Array), dispose() }`; `IExecTransport { exec(argv, { stdin?, stdout, stderr, signal }) -> { exitCode }, alive?(signal), remove() }` (`stdout`/`stderr` are `IOutputSink`s the workspace owns). `WorkspaceCreateOptions { runId, repo?, ref?, checkout?: { depth?, credential? }, image?, env?, limits?, deployment?, signal? }` (`repo` already normalized; `deployment` default `DEFAULT_DEPLOYMENT` `'default'`, a label value, `assertDeployment`). No `git` method: git is `exec(['git', ...])`. Workspace ids are `randomUUID()`, so `chamvi-ws-<id>` is a valid container name, pod name and label value. A provider builds `WorkspaceInfo { runId, provider, repo?, ref?, commit?, defaultBranch?, image?, createdAt, expiresAt }`, calls `prepareWorkspace(workspace, { ...checkout, repo, ref, signal })` and assigns its `{ commit?, defaultBranch? }` to the info; `IWorkspace.redact?(text)` exists on the manager's credential view only; a failed checkout disposes the workspace. `find` answers every live, unexpired workspace of the run in the deployment (the instance the process holds, else one rebuilt from what lives with the workspace) and never creates.
- **Rules** (every provider): exec takes argv only (`readonly string[]`, non-empty, no NUL); the only shells are the coding tools' `sh -c` scripts inside the workspace (the command a positional argument, never interpolated). Paths (`resolveWorkspacePath`) are relative to the root or under `/workspace/`, the model always sees `/workspace`; empty, NUL, other absolute paths and escapes are `ValidationError` before any filesystem or exec call. Output is capped per stream at `OUTPUT_MAX_BYTES` 65 536 (`createOutputCollector`: drains past the cap, holds at most the cap, a cut UTF-8 character dropped) with `stdoutTruncated`/`stderrTruncated`. Files have at most `FILE_MAX_BYTES` 16 MiB (plan 027c; was 1 MiB); `readBytes` returns the raw bytes, `readFile` decodes them strictly (`decodeUtf8File`, a file that is not valid UTF-8 is a `SandboxError`), `writeFile` takes UTF-8 text or bytes. Exec timeout default `EXEC_TIMEOUT_MS` 300 s, max `EXEC_TIMEOUT_MAX_MS` 1800 s, never past `expiresAt`; `timedOut` is a result. A command that cannot start exits 127.
- **Repositories** (`normalizeRepo`): `owner/name` -> `https://github.com/owner/name.git`, an https URL without credentials, query, fragment or a malformed percent escape (`decodeRepoPath`, which the credential lookups share), `file:///abs` only with `allowFileRepos`; `allowRepo(url)` narrows; the `ValidationError` never echoes the input. Refs (`assertGitRef`): `^[A-Za-z0-9][A-Za-z0-9._/+-]{0,254}$` without `..`, `//`, `@{`, `/.`, a trailing `/` or `.`, `.lock`. Checkout (`prepareWorkspace`, plan 027d, same on every provider, through the workspace's own exec): `git init -q .`, `git remote add origin <url>`, `ls-remote --symref <url> HEAD` (the default branch, `parseDefaultBranch`, dropped unless `isGitRef`), `fetch -q [--depth <n>] origin <ref or the default branch> [<default branch>]` (full history unless `checkout.depth`), `git checkout -q -B <ref> --track origin/<ref>` when `refs/remotes/origin/<ref>` exists, else `git -c advice.detachedHead=false checkout -q FETCH_HEAD`, `git rev-parse HEAD`, then `git config chamvi.defaultBranch <name>` (`CHECKOUT_DEFAULT_BRANCH_KEY`) and, last, `git config chamvi.checkout <sha>` (`CHECKOUT_KEY`); with an https `checkout.credential`, the workspace read credential helper is installed before remote calls; these keep the helper and disable hooks, while anonymous and file calls reset the helper and disable hooks; repo-less workspaces only `git init`, then `chamvi.checkout none` (`NO_REPO_CHECKOUT`). `readCheckout()` reads both back through one `git config --get-regexp` when a provider finds the workspace (`{ commit, defaultBranch? }`, `{}` repo-less, `undefined` when the checkout record is missing (git exits 1) or not fitting `info.repo`; any other failed read, e.g. right after a container restart, is retried on the provider's `IClock`, `CHECKOUT_READ_ATTEMPTS` 5 reads `CHECKOUT_READ_RETRY_MS` 500 ms apart): every provider's `find` skips a workspace without it, a create that died before its checkout finished (a process killed during the fetch), leaving it to the collection, and the manager never adopts a found workspace of a repository without `info.commit`. A failed step is a `SandboxError` with the first 2000 characters of git's stderr.
- **Environment and limits**: containers and pods get only `SANDBOX_ENV` (`HOME` = `WORKSPACE_HOME` `/home/sandbox`, a disk-backed volume of the workspace (Docker: anonymous volume, k8s: emptyDir), kept across a restart, never the memory-backed `/tmp`, so cargo, rustup, Maven, Gradle and mise's global config and shims stay out of the memory limit, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `safe.directory=/workspace` via `GIT_CONFIG_COUNT/KEY_0/VALUE_0`, `NPM_CONFIG_UPDATE_NOTIFIER=false`, `CI=true`) plus `CACHE_ENV` (`XDG_CACHE_HOME`, `npm_config_cache`, `PIP_CACHE_DIR`, `GOMODCACHE`, `GOCACHE`, `COMPOSER_CACHE_DIR`, each a folder under `CACHE_DIR` `/cache`; ## OpenClaw Channel

`openclawChannel({ name?, baseUrl, hooksToken, hooksPath?, agentId?, deliver: { channel, to, accountId? }, approvalUrl?, timeoutMs?, clock?, fetch? })` (`@chamvi/channel-openclaw`, the former `@chamvi/notify-openclaw`, global `fetch`, no runtime dependencies) is out only, default name `openclaw`, `defaultAddress` `deliver.to` (a tool may leave the address out). `out(message, address)`: `POST <baseUrl><hooksPath>/agent` (default `/hooks`, trailing slashes dropped, a base path kept; a `hooksToken` that is no valid header value, i.e. control characters, characters above U+00FF or surrounding whitespace, is `InvalidAgentDefinitionError`), `Authorization: Bearer <hooksToken>`, `Idempotency-Key` = `message.key`, or `sha256:<hex>` when it is over 256 characters or not visible ASCII (`transportKey`; OpenClaw silently ignores a longer key), body `{ message, name: 'chamvi', agentId?, deliver: true, channel, to, accountId? }` with `to` the address, or `deliver.to` for an empty one. The message is deterministic (no clock value or random id; OpenClaw starts a new run for a changed body under the same key): a relay instruction, title (when given), body cut to `MESSAGE_BODY_MAX_LENGTH` 8 000 (`cutText`: never ends on a high surrogate, appends `… (cut, <n> more characters)`), `Agent`/`Run`, and for an approval `Expires` and `Approve or deny: <approvalUrl({ runId, approvalId, agent })>`, else `APPROVAL_HINT`. `resumeTool` is gone: no message carries an MCP call, so OpenClaw's MCP principal needs only `agent:<name>:run` and never `agent:<name>:approve`; approval links carry ids only (suggested `https://<app>/ui/approvals?run=<runId>&approval=<approvalId>`, the signed-in owner answers through `POST /runs/:id/approve`). Any 2xx resolves; otherwise `OpenClaw <status>: <text>` (`(retry after <v>)` for `Retry-After`), `OpenClaw request failed: <message> (<cause message>)`, `OpenClaw did not answer within <ms>ms.` (code `openclaw_request`), bounded by `timeoutMs` (30 s) on the `IClock`; the response text has `hooksToken` replaced by `[redacted]`, then is cut to 500 characters. `openclawModule()` (`@chamvi/channel-openclaw/module`, module name `chamvi:channel:<name>`) reads `OPENCLAW_*` env, links approvals from `CHAMVI_PUBLIC_URL` and contributes the channel to `AppToken.CHANNELS`; tools use `ctx.channels.findOne(name)` (the context pair is gone). Verified OpenClaw facts (2026-10-21): hooks off by default, `channel: 'last'` and partial destinations are 400, bodies over 256 KiB 413, `200 { ok, runId }` means admitted (not delivered), replay entries live in memory for 5 minutes after completion and a restart clears them, so chamvi's records (the emit effect, `waiting.notifiedAt`) are the primary dedupe. OpenClaw runs an agent turn on the message and treats it as external content.

A choice approval (plan 031b) adds a section after the body, `Options (choose one):` (or `choose one or more`) plus `- <id>: <label>` per option (no detail), and its link line reads `Choose and approve or deny: <link>`, else `CHOICE_HINT` (internal).

## Web Tools

`@chamvi/tool-web` holds `webTools({ client?, lookup?, allowUrl?, maxBytes?, timeoutMs?, clock? })`, one plain `defineTool()` tool, `web_fetch`, that runs in the chamvi process; it peers on core and `ai` and depends on `hapic` (requests and proxy), `mdream` (HTML to markdown or text, a Rust core with prebuilt binaries per platform and a WASM fallback) and `smob`. Options are checked when called (`InvalidAgentDefinitionError`).

- **Request** (`getPage()`, `request/module.ts`; the URL check in `url/`, the options in `options/`): a GET through the hapic client (default `createClient()`, whose `FetchTransport` takes the proxy from `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`) with `redirect: 'manual'` and `responseType: 'stream'`; redirects followed by hand (at most `WEB_MAX_REDIRECTS` 5); before every hop `parseWebUrl` (http(s) only, no credentials, `ValidationError`) and `checkUrl` (`allowUrl(url)`: `true` allows, `false` refuses, `undefined` resolves the host through `lookup` (default `dns.lookup`, every address) and refuses a host with any address `isBlockedAddress()` holds, `ValidationError`); the body read up to `maxBytes` (default `WEB_FETCH_MAX_BYTES` 5 MiB, the rest cancelled, `truncated`); `timeoutMs` (default `WEB_TIMEOUT_MS` 30 s) on the `IClock` over the whole fetch; a 4xx/5xx status, a network failure and the timeout are `ChamviError`s with code `web_request` (`WEB_REQUEST_ERROR_CODE`), tool errors. The request resolves the name again, so DNS rebinding and a proxy's own connect are not covered (documented; an egress policy is the operator's tool).
- **Address check** (`address/`): `parseAddress()` (IPv4/IPv6 to bytes, brackets and a trailing dotted quad allowed), `isBlockedAddress()` over `BLOCKED_IPV4`/`BLOCKED_IPV6` (this network, RFC 1918, CGNAT, loopback, link-local and metadata, multicast, reserved, documentation, benchmarking; IPv4-mapped, NAT64 and 6to4 judged by the IPv4 inside; anything that is no IP address is blocked).
- **`web_fetch({ url, format?, offset? })`** (`tools/fetch.ts`): a type that is no text (`isText`: `text/*`, JSON, XML, scripts, `+json`/`+xml`, none) is a `web_request` error; the body decoded by its charset (or `<meta charset>`, else UTF-8); an HTML page converted inline by mdream to markdown (`htmlToMarkdown`) or text (`htmlToText`): links and images absolute against the page URL, `javascript:` and `data:` links turned into their text (`clean.emptyLinks`), the main content isolated (`minimal`), and for a page without main or article (or a fragment, which isolates to nothing) the whole body without `PAGE_CHROME_ELEMENTS`; the title read through mdream's frontmatter callback, the frontmatter stripped; `raw` returns the body; at most `WEB_FETCH_MAX_CHARS` 65 536 characters from `offset` (never inside a surrogate pair, an offset past the end a `ValidationError`), `nextOffset` while more follows. Package registries are plain JSON URLs the description names (`https://registry.npmjs.org/<name>`, `https://pypi.org/pypi/<name>/json`); there is no registry or search tool.

## App and CLI

`@chamvi/app` (library, no process concerns) turns `export default createApp({ agents, modules?, models? })` into a running app; `@chamvi/cli` (bin `chamvi`, citty only) adds argv, entry loading, signals and exit codes. Contract: `.agents/plans/011-deploy-kit.md` C1 to C5 while it lives.

- **App**: `createApp()` is synchronous and side-effect free (refuses options that are no object or an `agents` that is no array (no agents at all is allowed: `chamvi:agents` logs `NO_AGENTS_MESSAGE` as a warning when there is no agents dir either), a `modules` entry that is no `IModule` object, since orkos would `import()` a string, and a name used twice, a built-in's included) and branded (`APP_BRAND`, `isApp()` matches another installed copy). Each lifecycle (`start({ env?, dev? })`, `check({ env?, dev? })`, `runJob({ agent, subscription?, env? })`, `migrate({ env? })`) builds one orkos `Application` over a fresh eldin `Container` with `AppToken.CONTEXT` (`mode` `start`/`job`/`migrate`, `dev`, `env`, the stop `signal`, `report`, `models`, `agents`, `check: true` for `check()`, `job: { agent }` for `runJob()`) registered first; an app runs one lifecycle (`app_in_use` after it, also after `stop()`). orkos graph errors (a dependency the app does not register, a cycle, a version mismatch) become `InvalidAgentDefinitionError` (`toSetupError()`). `stop()` is memoized: it aborts the context signal (`app_stopped`), waits for the lifecycle in flight, tears down; a setup error answered by `app_stopped` is logged, never lost; every teardown error is reported (orkos swallows them, `reportingModule()`) and `stop()` (or a job's teardown) then rejects with `app_stop_failed`. - **Modules**: built-ins in order `chamvi:config`, `chamvi:store`, `chamvi:static-tokens`, `chamvi:engine`, `chamvi:agents`, `chamvi:scheduler`, `chamvi:http` (`ModuleName`), each replaced in place by a user module of the same name, then the user modules. `setup` contributes to the collection tokens (`HTTP_ROUTES`, `CHANNELS` (every `IChannel` the engine registers: the engine module's `agent` channel (`agentChannel()`, start and job mode, so a user channel named `agent` clashes), the scheduler module's `cron` channel, the http module's `http`, `mcp` and `webhook`, `consoleChannelModule()`'s, the feature modules'; names unique, a clash fails the setup with `InvalidAgentDefinitionError`), `AUTHENTICATORS` with an `order`, `LIFECYCLE_HOOKS`, `GIT_CREDENTIALS` (git credential sources, structurally `GitCredentialSource`, for `sandboxModule()`; `githubModule()` contributes its App's)); `onReady` consumes (engine: channels; http: authenticators, routes, every contributed channel with an `in` for `createHttpApp({ channels })`), so contributions need no order; a module resolving `ENGINE` or `SERVER` in `onReady` lists it in `dependencies`. Hooks: `engineCreated` (start, job and a check), `started`, `stopping` (first in the shutdown, before the drain stops the channels), `drained` (after the engine drained, before the store closes); a throwing hook is reported, the others run. The static-tokens module contributes `CHAMVI_TOKENS` in `setup` and, in dev without any other authenticator, a random `*` token (id `dev`, logged once) in `onReady`; http lists it as an optional dependency. Optional modules live in the feature packages on a `/module` subpath (`@chamvi/github/module` `githubModule`, `@chamvi/channel-openclaw/module` `openclawModule`, `@chamvi/sandbox/module` `sandboxModule`, `@chamvi/ui/module` `uiModule`; `@chamvi/app` an optional peer there, `src/module/` the only folder importing it, kept external in `dist/module.mjs` so one `AppToken` set exists per process) and contribute their channel to `CHANNELS` or provide their instance in the `engineCreated` hook through the package's context pair; a throwing `engineCreated` hook (e.g. a second provide of one key) is caught by `runHooks` and reported through `context.report()`, the app still starts. `@chamvi/app` keeps only `/authup` (`authupModule`, `oidcModule`: moving them to `@chamvi/http` would make http depend on app, a cycle) and `/testing` (`buildModuleHarness()`/`createModuleHarness()`: the real lifecycle over the given modules, `reportingModule` and `runStartSteps` included, `reported` collecting `context.report()`), and its main entry exports the module contract (`AppToken`, `ModuleName`, `AppContext`, `ILifecycleHook`, env readers, `approvalUrlOf`, the orkos `IModule` and eldin `IContainer` types). ## Approved local skills (`@chamvi/app`)

`hashSkillBundle(directory)` validates and hashes passive UTF-8 bundles; it is a separate review aid, never dynamic approval. `loadSkillBundles(approved)` synchronously verifies explicit `{ name, version, directory, sha256 }` descriptors and returns an immutable `SkillCatalog` (`skills`, metadata-only `instructions`, ordinary SDK `tools`). No I/O on import. Operators append instructions and compose tools explicitly, checking for a `load_skill` collision. `SkillMetadata.ignoredFields` reports extra frontmatter keys; settings such as `allowed-tools`/`model` have no effect.

The fixed `load_skill({ name, reference? })` returns `LoadedSkill` (identity, `reference: null` for body, exact decoded content and sorted supporting paths) from private snapshots, with no runtime filesystem reads or activation state. Normal tool policy, hooks, approvals and checkpoints apply; repeated/parallel disclosure and approval recovery use existing engine behavior. `InvalidAgentDefinitionError` rejects invalid setup, `ValidationError` rejects model requests, and neither diagnostic exposes bodies. Core has no dependency on bundle filesystem code.

Pins cover every supported regular file with length-framed SHA-256, including README/references that agent-folder hashing may ignore. Bounds: 16 bundles, 64 files, 1 MiB total, 4 KiB frontmatter, 64 KiB body, 128 KiB/supporting file, 1,024 inventory entries including root/directories and 64 directory levels. Supported suffixes `.md`/`.txt`/`.json`/`.yaml`/`.yml` and exact basenames `LICENSE`/`NOTICE` are passive text only; reject symlinks, special/hidden/unsupported files, malformed UTF-8, NUL text and control-bearing paths, metadata keys or trimmed descriptions. Surrounding description whitespace is trimmed before nonblank/1,024-character/control checks; internal controls remain invalid. YAML references, including agent metadata, are opaque text and are never parsed as configuration. Versions are exact reviewed identifiers, not rolling labels/ranges. Keep operator directories immutable and not attacker-writable during setup; filesystem checks are not a malicious-host-writer security boundary.

Disk edits cannot alter an existing catalog; recreation with changed bytes under the old pin fails closed. Upgrade reviewed assets and the tracked descriptor pin together. External directories have no watch or automatic revision integration. Skills grant no tools, permissions, scripts, subagents or sandboxing. Repository instructions (separate plan 035) and issue text cannot add approvals. Complex third-party workflows, including Cloudflare audit scripts and independent subagents, require an explicit passive adaptation and separately supported capabilities. Credential isolation/private disclosure, future compaction retention and delegation remain separate work. Public usage and complete bounds live in `packages/docs/src/guide/skills.md`.

## Errors

All errors extend `ChamviError` (ebec `BaseError`) with a `code`: `InvalidAgentDefinitionError` (also every model and provider problem: an agent with no model and no default, a provider that is not configured, a missing key or package, a malformed setting; a tool error from `resolveModel` in `execute`), `BudgetExceededError` (`BudgetExceeded`), `FatalToolError`, `IncompleteResponseError` (`incomplete_response`), `ContextNotProvidedError` (`context_not_provided`, a tool error in `execute` and effect hooks, a failed run from the tools factory), `RunNotFoundError`, `ArtifactNotFoundError` (`artifact_not_found`), `InvalidRunStateError`, `LeaseLostError`, `TimeoutError` (`Timeout`), `ToolNotAllowedError` (`tool_not_allowed`, only ever a tool error), `ToolDeniedError` (`tool_denied`, a gate's refusal, only ever a tool error), `ChannelNotFoundError` (`channel_not_found`, `ctx.channels.findOneOrFail()` for an unknown channel or one without `out`, and an approval delivery through a channel the engine no longer has, to `onError`), `AgentNotFoundError` (`agent_not_found`, `dispatch` for an agent the engine does not hold, http 404), the run-only codes `agent_replaced` and `agent_removed` (`ErrorCode.AGENT_REPLACED`/`AGENT_REMOVED`, stored on runs a registry change cancelled, no class), `SandboxError` (`sandbox_error`, a workspace or provider failure, only ever a tool error), `ValidationError`; the codes are `ErrorCode` (`errors/constants.ts`); outside core three more codes exist: `github_request` (`@chamvi/github`'s tool errors, never fatal, and its channel's send failures), `openclaw_request` (`@chamvi/channel-openclaw`) and `web_request` (`@chamvi/tool-web`'s request failures, never fatal). A failed run stores `{ code, message }` in `run.error`.
